# 2026-10-31：第二张卡纯当热专家池（异构卡）

目标硬件是一张快卡带一张慢卡，比如 RTX PRO 5000 72 GB + RTX PRO 4500 32 GB、RTX 5090 + RTX 5070 Ti。这种组合用张量并行时，两张卡都只能按小卡的显存和慢卡的速度跑。这次让第二张卡不放模型，只多放热专家（`XTIER_GPU2_SLOTS`，默认关）。用法：

```
XTIER_GPU2_SLOTS=auto CUDA_VISIBLE_DEVICES=快卡,慢卡 bash configs/qwen38-rtx4090-3090/run-qwen.sh
```

**结论**：两张 RTX 4090 模拟 24 + 16 GiB，Qwen3.8 decode 比同样配置的 TP 快 12–13%，比单卡快约 28%；让第二张卡约慢 1.2 倍，只掉 3–5%。两张卡一样时 decode 还是 TP 更快。真实的异构卡还没测过。

## 做法（`xtier/cache/second.py`，`csrc/mailbox/mailbox.cpp` 的 `g2_*`）

主卡的 decode 图一点不变：还是打包、请求信箱、把返回的结果加上去。改动都在信箱调度线程里：

1. **拆路由**：CPU 开始算之前，查第二张卡的驻留表（在内存里）。主卡没命中、第二张卡有的路由，给 CPU 标成 −1（引擎本来就跳过 −1），写进一块控制块。
2. **启动图**：第二张卡上每层每种形状捕获一张 CUDA 图（第一次遇到这个形状时捕获），调度线程启动它（约 4–10 µs）。图的内容是：`_fetch` 从锁页内存读控制块和激活值 → 和主卡相同的 `_gate_up`、`_down`、`_combine` → 结果写回内存 → 置完成标志。
3. **合并**：CPU 算完后等完成标志，把第二张卡的结果加到 CPU 的输出上，再回复信箱。

prefill 只在主卡上算，所以首字不变。开发时实测发现并改掉的三点：

- **两张卡放不同的专家**：主卡的策略原来会把第二张卡已有的专家搬走，第二张卡那个槽就白占了，第一版命中率只有 0.74。现在第二张卡有的专家，主卡不再换入；第二张卡优先淘汰主卡已有的、其次最冷的。命中率升到约 0.84–0.88。
- **内核读写内存，不用复制引擎**：换专家的大块上传占着复制引擎，控制块排在后面要等。这条和上一条一起改后，第二张卡每次调用从约 110–150 µs（2.4 个专家）变成约 80–105 µs（5 个专家）。
- **自动平衡**：一次调用要等 CPU 和第二张卡都算完。调度线程每 256 次调用统计一次第二张卡最后完成的比例：超过 60% 就减少每次分给它的专家数，低于 40% 就增加。

精度：第二张卡用和主卡同样的内核（W4A16、FP32 累加），只有 FP32 相加的先后可能不同。

显存：`auto` 把第二张卡的空闲显存减 1.5 GiB 都放专家。所有形状（m = 1–8，48 层）的图都捕获后只多占 36 MiB；24 + 16 GiB 时还剩约 780 MiB。某个形状的图放不下时，这个形状退回 CPU 算，服务不受影响。

## 实测

租用的云主机：2 张 RTX 4090 24 GB（同一 NUMA，没有 P2P）、Xeon 8352V（AVX2 引擎）、容器 32 个 CPU、240 GB 内存，引擎 30 线程。Qwen3.8 Flash Next 整模型，无 MTP，单请求，输出 512 token（`bench/context_speed.py`，`--warmup 8192 --repeats 2`），速度单位 tok/s：

| 配置 | 每层热专家槽 | 32K decode | 120K decode | 120K 首字 | 命中率 |
|---|---|---:|---:|---:|---:|
| 单卡 24 GiB（基准） | 48 | 41.0（100%） | 43.6（100%） | 60.9 s（100%） | 0.60 |
| 同规格卡 TP 24 + 24 GiB | 180（半个专家） | 62.1（151%） | 63.4（145%） | 68.9 s（88%） | 0.92 |
| 异构卡 TP 24 + 16 GiB | 64（半个专家） | 51.1（125%） | 49.4（113%） | 60.0 s（101%） | 0.72 |
| 同规格卡热池 主 24 + 热池 24 GiB | 48 + 178 | 58.2（142%） | 56.2（129%） | 59.3 s（103%） | 0.86–0.93 |
| **异构卡热池 主 24 + 热池 16 GiB** | **48 + 113** | **57.3（140%）** | **55.9（128%）** | **58.9 s（103%）** | **0.84–0.88** |
| 异构卡热池 主 24 + 热池 16 GiB，热池卡耗时约 1.2 倍 | 48 + 113 | 54.5（133%） | 54.2（124%） | 59.0 s（103%） | 0.82–0.85 |

- **16 GiB**：用 `tools/vram_limit.py` 占住第二张卡的显存。
- **百分比**：相对单卡的速度，单卡 = 100%；首字 = 单卡耗时 ÷ 本行耗时。
- **基线**：单卡和两组 TP 是当天早些时候测的，同一台机器、同样的测速参数，但顺序不同：单卡跑在照抄之后，同规格卡 TP 跑在照抄和 PPL 之后，其他行都是新起服务直接测。
- **单卡这一行偏慢**：同样 48 槽、新起服务（64K 上下文）又测过一次，32K decode 44.7 tok/s、首字 19.4 s，这里是 41.0、20.5 s，命中率相同，每层 CPU 调用更慢。按 44.7 算，异构卡热池 32K 是 128%，不是 140%。120K 没有第二次测量。
- **首字其实差不多**：热池不参与 prefill，开第二张卡时 32K 首字 18.7–19.5 s，和新起服务的单卡 19.1–19.4 s 相同，表里的 103% 不是加速。同规格卡 TP 的 68.9 s 里有一次约 9 s 的卡顿：32K 和 120K 各有一个分块约 13 s（平时约 4 s），其余分块和别的行相同；同样 180 槽、新起服务的 32K 首字是 19.1 s。卡顿的原因没查。
- **24 + 24 GiB 时池和 24 + 16 GiB 差不多**：多放专家已经不是短板了。这时每步约等于 12.5 ms + 48 ×（第二张卡每次调用约 100–110 µs），瓶颈是第二张卡这次调用的耗时。
- **同规格 TP 更快**：TP 180 槽时每层只等 CPU（约 65 µs）；池要多一次 PCIe 往返和图启动，每层约 100–110 µs。

这台机器的 CPU 偏弱（每个未命中专家约 35 µs），所以第二张卡省下的时间多。CPU 越强，第二张卡省的越少，平衡也会分给它更少的专家。真实的 PRO 5000 + PRO 4500、5090 + 5070 Ti 还要实测。

### 怎么模拟慢卡

容器不能改频率和功耗。试了三种办法，只有最后一种可用：

1. **MPS 限 SM**：`CUDA_MPS_ACTIVE_THREAD_PERCENTAGE` 是进程启动时读一次、所有卡一起生效的，只限第二张卡做不到（进程启动就设 75%，两张卡的 GEMM 都从 19 ms 变成 24 ms；主卡上下文建好后才设，第二张卡不变）。所以这个办法只用来校准（见下表）。第一次的“75% SM”整模型数据（56.9 / 55.5）实际没限住，已作废。
2. **调度线程里把第二张卡的耗时拉长**：CPU 算完才能看到完成标志，拉长的实际是 CPU 和第二张卡里较晚的那个；平衡被骗到每次只分 1 个专家（37 tok/s），和真卡的行为不同，已删掉。
3. **图里加真实负载**（`XTIER_GPU2_SLOW=1`，仅供测试）：第二张卡每次调用多算一遍 `_down`，结果不变。每次调用约 102 → 120 µs，完成标志真的变晚，平衡把每次的专家数上限从 6–7 降到 5–6。上表用的是这个。

在一张卡上用 MPS 实测少了 SM 后，GPU 部分含内存往返的耗时（单层，每次调用 1 个 token）：

| 专家数 | 100% SM | 75% SM（≈ PRO 4500 / PRO 5000） | 41% SM（≈ RTX 5070 Ti / 5090） |
|---:|---:|---:|---:|
| 5 | 53 µs | 53 µs（1.0 倍） | 61 µs（1.15 倍） |
| 10 | 53 µs | 70 µs（1.3 倍） | 86 µs（1.6 倍） |

一次调用的专家不多时，程序块比 SM 少，少一些 SM 也排得开。实际运行时平均每次约 5 个专家，所以约慢 1.2 倍对 PRO 4500 是合理的估计。这张表没有包括显存带宽（PRO 4500 是 PRO 5000 的 67%），也没有包括频率差别。

## 验证

- **单层**（`tests/second_gpu_check.py`，真实权重，m = 1–8 共 12 次调用）：同样 120 个专家放第二张卡和放主卡，结果**逐位相同**；Qwen3.8、GLM-5.3、DeepSeek V4.1 三种格式都是 12/12。两张卡拆开放时，相对误差 5e-8，只差 FP32 相加的先后。
- **PPL**（Qwen3.8，1K × 10 段）：与 TP 基线平均差 +0.0024。PPL 走 prefill，不经过第二张卡，这里只说明没有影响 prefill。
- **GLM-5.3 截层服务**（8 层、开弹性槽）：第二张卡 228 槽，服务正常，没有报错。截层模型的输出没有意义，这里只验证能跑。
- **DeepSeek V4.1**：只测了单层，整模型没在第二张卡上跑过。
- **运行中遇到新形状**：捕获不影响调度线程（第一版在回放用的流上捕获，会崩，已改成单独的流）。
- **那台机器的物理 1 号 4090**：算第 8 个 token 时结果会抖（单层相对误差约 1e-6），老路径也一样，跟着卡走（`CHECK_REPS=300`，交换两张卡验证）。decode 只用 m ≤ 2，碰不到。

### 照抄：提示词 KV 引起的翻转

温度 0 照抄 8 段（`bench/copy_test.py`），开第二张卡时一共启动 9 次：6 次全部 0/8；3 次（第一版、一次全速、一次拉长耗时的模拟）都翻了同一处，第 2 段的 `PREFILL_TRUNCATION` 抄成 `PREFILL_TRUNCATE`，同一台服务上单请求和两请求都翻。

排查过程：

- 查历史记录：10-30 的单张 RTX 3090（62 槽，没有第二张卡的代码）翻过同一处。
- 在不翻的服务上量这个 token：`ATION` 领先 8–9 nats，`ATE` 约 −15。这个差距不是 FP32 相加先后能造成的，所以“接近平局”的解释不成立。
- 同一台服务清掉提示词缓存（`/flush_cache`）重算 KV 后，`ATE` 从 −15.4 变成 −5.9。说明起作用的是提示词的 KV：它算一次后留在缓存里，所以同一台服务内要么全翻，要么全不翻。
- **单张 4090、进程里没有第二张卡**，反复清缓存重新生成 16 次：`ATE` 在 −16.1 到 −0.7 之间摆动，中位数 −14.7，**1 次真的翻了**（`ATE` 和 `ATION` 都是 −0.697）。

所以这个翻转和第二张卡无关，prefill 也不经过第二张卡。但同一提示词重算，某个 token 的 logprob 能摆 15 nats，这个幅度不像舍入误差，而且有几个值精确重复，像是几种离散情况。原因还没查，单独记下了。

RTX PRO 5000（NVFP4 KV、开投机解码、112 线程）上做同样的测试，也有同样的摆动：16 次里 `ATE` 在 −16.1 到 −1.1 之间，这次没翻；−2.35、−2.70 这几个值和 4090 上几乎一样。工具是 `bench/token_flip.py`。

## 主线回归（功能关）

代码合进主线后，确认功能关时不影响原来的服务。

测试条件：
- **硬件**：单卡 RTX PRO 5000，功耗墙 300 W。
- **参数**：启动台默认参数（512K 上下文、加速包、投机解码、快速加载）。
- **对比口径**：和 [10-30 的回归](2026-10-30-sglang-6162b07.md)同样的测法。
- **最后一处改动**：DS、GLM 的全部测试和 Qwen 的照抄、dsh 跑在最后一处改动之前的库上。这处改动只在第二张卡的路径里（模拟慢卡的开关），功能关时走不到；改完后重新编译，信箱和缓存的单层测试通过，Qwen 的 PPL、长上下文是在最终的库上跑的。

| 项目 | Qwen3.8 Flash Next | GLM-5.3 Flash | DeepSeek V4.1 Flash 1017 |
|---|---|---|---|
| 启动到在线 | 259 s | 269 s | 187 s |
| 照抄（单路 / 两路） | 0/8、0/8 | 0/8、0/8 | 1/8、0/8 |
| PPL（这次 / 10-30） | 3.4802 / 3.4812 | 3.9983 / 3.9974 | 3.3204 / 3.3183 |
| 64K 冷 prefill 首字（这次 / 10-30） | 12.2 / 12.2 s | 25.2 / 25.3 s | 13.6 / 13.6 s |
| 64K decode 每步（这次 / 10-30） | 14.6 / 14.5 ms | 28.4 / 28.9 ms | 29.4 / 29.6 ms |
| 52 万 token（满上下文） | 不 OOM，首字 109 s | 不 OOM，首字 207 s | 不 OOM，首字 114 s |
| dsh 15 分钟 | 73 轮 0 失败，回忆 3/3 | 40 轮 0 失败，回忆 3/3 | 23 轮 0 失败，回忆 3/3 |
| 日志 | 0 错误 | 0 错误 | 0 错误 |

- **DeepSeek 单路照抄的 1/8**：结尾多出 `</src>`，正文逐字一致，是之前就记过的现象。
- **DeepSeek 52 万 decode**：88 tok/s，10-30 是 102。每步 34.5 / 34.0 ms 基本不变，差别来自投机接受长度（3.03 / 3.45），同一配置下这个值本来就有波动。
- 三个模型的日志里都没有第二张卡相关的输出，确认功能确实是关的。

## 开关

| 环境变量 | 默认 | 作用 |
|---|---|---|
| `XTIER_GPU2_SLOTS` | 关 | 第二张卡每层的槽数，或 `auto` |
| `XTIER_GPU2_RESERVE_GIB` | 1.5 | `auto` 时留给上下文、缓冲区和图的显存 |
| `XTIER_GPU2_DEVICE` | 主卡的下一张 | 第二张卡的编号 |
| `XTIER_GPU2_BALANCE` | 1 | 自动平衡 |
| `XTIER_GPU2_ADAPT` | 1 | 第二张卡自适应换专家 |
| `XTIER_GPU2_SWAPS` | 64 | 每轮最多换几个专家 |
| `XTIER_GPU2_MIN_USE` / `_MIN_GAIN` | 0.5 / 0.25 | 换入的最低路由计数 / 最低增益 |
| `XTIER_GPU2_SLOW` | 0 | 仅供测试：第二张卡每次调用多算 n 遍 `_down`，模拟慢卡 |
