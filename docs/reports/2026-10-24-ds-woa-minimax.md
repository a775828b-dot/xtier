## DeepSeek：decode 每步慢 6% 的原因

10-24 的 agent 测速里 XTier 长回复每步 33.9 ms、生产 32.0 ms。两边用同一个只开 GPU 活动的 torch profiler 抓 decode
（`xtier-dev/decode_profile.py`：同一个 16K 提示，decode 开始 4 秒后录 3 秒；XTier 91 步、生产 99 步），逐 kernel 对比：

| 每步（DSpark 验证 6 token） | XTier | 生产 | 差 |
|---|---:|---:|---:|
| 跨度 | 33.73 ms | 30.94 ms | +2.79 ms |
| 整卡空闲（等 CPU 专家、调度） | 3.81 ms | 2.32 ms | +1.49 ms |
| **wo_a（注意力低秩输出投影，40 层 + 草稿 3 层）** | 3.23 ms：cuBLAS SM80 WMMA BF16，75 µs × 43 | 1.40 ms：lkqmoe 的 Triton FP8，35 µs × 40 | **+1.83 ms** |
| hc_mix 两个 kernel | 1.47 ms | 1.01 ms | +0.45 ms（旁路流，与主流重叠） |
| 索引器（FP4 logits + top-k） | 0.56 ms | 0.12 ms | +0.44 ms |
| 稀疏 MLA decode | 0.83 ms | 1.10 ms | −0.27 ms |

- **wo_a 是主因**：官方 main 的 FP8 wo_a GEMM 只认 128 × 128 块缩放，DeepSeek V4.1 的 wo_a 是 32 × 32 的 E8M0 块，于是加载时
  反量化成 BF16，decode 走 `torch.einsum`，cuBLAS 在 SM120 上选了 SM80 的 WMMA 批量 GEMM。生产用的是 lkqmoe 的 Triton 分组
  einsum，权重保持检查点的 FP8。
- 索引器：SM120 不走官方的分页路径（只给 SM90），每层先 gather 再算 Triton FP4 logits、再 torch.topk；生产用 DeepGEMM 的
  `sm120_fp4_paged_mqa_logits` 加融合 top-k。每步 0.44 ms，留作下一步。
- hc_mix：官方 main 把 `_HC_MIX_NUM_STAGES` 改成 1（B300 / H200 实测更快），生产仍是 2；XTier 里它跑在旁路流上，不在关键路径。

## 修复：加速包 `deepseek_v4/wo_a.py`（FP8 wo_a + Triton 分组 einsum）

- 加载时截下检查点的 E8M0 缩放，把每层 BF16 wo_a 还原成检查点的 FP8：E8M0 是 2 的幂，还原是精确的，逐层核对"FP8 反量化 ==
  加载的 BF16"逐位相等、且 kernel 与官方 einsum 在随机输入上相对误差 ≤ 1e-3，不过就保留 BF16。40 层全部转换，显存省 1.25 GiB。
- 16 token 以内（decode、两个请求的 DSpark 验证）走一个 Triton kernel：每个权重块先在寄存器里还原成同样的 BF16 值再做点积，
  FP32 累加，与 cuBLAS 只差求和顺序。更大的调用（prefill）把该层反量化到一块复用的 BF16 缓冲，仍走官方路径。
- 草稿模型（自己的类、BF16 权重）调用同一个函数，用这个 kernel 的 BF16 形式。
- 单测 `tests/ds_wo_a_check.py`（真实层，权重轮换出 L2）：cuBLAS 70.7 µs，Triton BF16 56.9 µs，FP8 30.0 µs（BLOCK_R 32；
  lkqmoe 的 BLOCK_R 128 是 32.5 µs）；与 cuBLAS 相对误差 ≤ 4e-5，99.99% 输出逐位相同。

修复后同口径剖析：**每步 30.47 ms（生产 30.94 ms）**，整卡空闲 2.33 ms（生产 2.32 ms）。照抄测试单请求、两请求各 8 段 0 错。

## Qwen、GLM 换 agent 速度时遇到的两个问题

- **GLM 在第一个工具请求时死掉**（XTier，WebUI 启动）：`Failed to CUDA calloc 536870912 bytes`（NCCL）。SGLang 的 sampler 只要请求带
  语法约束（GLM 的 glm47 工具调用解析会用）就对 TP 组做一次 token id 的 all-reduce，只按开关、不按组大小跳过；TP 1 时这次 all-reduce
  是恒等，但第一次调用会让 NCCL 建通信器并直接 cudaMalloc 512 MB，而 64K 冷 prefill 之后显存已满。10-24 夜给 GLM 补上工具调用解析器
  之后才会走到这里。修正（`xtier/platform.py`，与模型无关）：组里只有一个 rank 时跳过这次调用。
- **agent_bench 遇到非法 JSON 的工具参数整轮中断**：Qwen 的 `qwen3_coder` 解析偶尔给出不是合法 JSON 的参数，生产版 agent_bench 把它原样
  写进历史，下一个请求 SGLang 回 400（"Assistant tool call function.arguments must be valid JSON"）。仓库 `bench/agent_bench.py` 是生产
  lsglang_ds4.1 641931f 那份加两处健壮性修正（历史里记 `{}`、模型照样在工具结果里看到解析错误；单个请求出错只结束该会话），计时不变；
  Qwen、GLM 的 XTier 和生产都用它，DeepSeek 两边用的是生产原版。

## dsh 真机调用（本机 dsh 无头模式 → 服务器 8000 → XTier）

本机 DeepSeek Harness 的 dsh（`dsh --profile headless`，补丁 `xtier-headless.yml`：8000 入口作为 provider `home`，工作区内写入不需审批），
每个模型一个约 10 分钟的真实编码任务，在新的空目录里做完并自测：

| 模型（XTier，WebUI 控制台启动） | 用时 | 结果 |
|---|---:|---|
| DeepSeek V4.1 Flash 1017 | 6.9 min | `ledger` 记账包（SQLite、整数分、add / list / summary / remove / export、中文 README），14 个测试全过 |
| Qwen3.8 Flash Next | 0.7 min | 按任务做完：`gen_log.py`（300 行日志）、`logstat.py`（状态码 / 最慢路径 / 每小时、`--top N`）、`test_logstat.py` 11 个测试全过、`report.md` |
| GLM-5.3 Flash | 1.1 min | 按任务做完，同样五个文件，8 个测试全过（中途自己发现一条断言的预期写错并改正） |
| MiniMax-M3.1-Flash（10-24 上午，加速包默认配置） | 2.9 min | 按任务做完，同样五个文件，7 个测试全过（中途自己发现沙箱不让在工作区外建临时目录、report.md 的编码不对，都改正了） |

- 无头模式的两个坑（客户端侧）：headless profile 不读桌面版凭据服务里的 `HOME_API_KEY`（运行脚本从 `~/.dsh/.credentials.yaml`
  取值只传给子进程）；`dsh.cmd` 是批处理，多行任务参数在 cmd.exe 里被截到第一行（改成任务写文件、从 stdin 读 `-`）。
  DeepSeek 那次只收到第一行（"在当前目录完成一个小项目，全部用 Python 标准库："），自己定了一个项目做完，照样是一次完整的真机调用。

## deepseek-recipe 分词（634ee17）

DeepSeek 官方的 deepseek-recipe 只把模板的控制 token、图片占位和 grounding token 当特殊 token；SGLang 把渲染后的整段提示一次
encode，消息内容里出现的 `<｜User｜>`、`</think>` 一类拼写会变成控制 token（编码代理读到的源码里常见），长对话每轮整段重编码
（568K token 1.3 s）。加速包把内容里的这些拼写换成私用区占位，按模板的 added token 切段，各段用不带 added vocab 的分词器批量编码
（同一段 0.18 s），结果与 deepseek-recipe 0.2.0 的官方对照逐 token 一致（`tests/ds_recipe_tokens_check.py`）。

## MiniMax-M3.1-Flash：SM120 上跑起来需要的修正

SGLang 对 MiniMax M3.1 的支持还在 PR #45925（未合入 main），装在单独的 venv（env-m31），其余三个模型仍用 main 8cd3c494。
在 RTX PRO 5000（SM120）上，PR 的代码有四处把 SM120 当成 SM100 处理，逐个以 hook 修正（`xtier/packs/minimax_m3/`，不改 SGLang）：

1. 参数解析：NVFP4 检查点在"Blackwell"上选原生栈（MSA-v1 Q8KV4 注意力 + 打包 NVFP4 KV、MegaMoE、FP8 KV + TRT-LLM MHA），这些内核
   只有 SM100 / SM103（tcgen05），而 TRT-LLM 的 FMHAv2 prefill 在 SM120 上拒绝 FP8 KV，服务在解析参数时就退出。SM120 改用 SGLang 给
   Hopper 的通用栈：MiniMax 稀疏注意力的 Triton 路径，外面套 TRT-LLM MHA 稠密后端（Hopper 的 FA3 只有 SM90），页大小 128，专家
   scheme 照 Hopper（Marlin；专家反正由 XTier 跑）。KV 仍是检查点声明的 FP8 E4M3（Triton 稀疏路径读时反量化），只是不写进参数。
2. 原生栈判定 `uses_minimax_m3_nvfp4_native_stack` 在 SM120 返回 False（KV 池、注意力后端、显存预算三处要一致）。
3. 专家 scheme `MiniMaxM3Nvfp4MoE` 在 SM120 按 Hopper 初始化（否则要求 MegaMoE 或 TRT-LLM routed）。
4. DSpark 的 target verify：通用稀疏后端只在 NPU 和 ROCm 上实现了 verify（CUDA 上 DSpark 只配原生栈），verify batch 走进 prefill
   路径、第一次 forward 就因为没有 extend 长度而失败。照 ROCm 的做法：每个草稿行作为一个因果 decode 查询走 Triton 稀疏 decode，
   长度 = 已接受前缀 + 行号（元数据在 graph 里捕获），捕获时 KV 长度上界取上下文长度。

另外两处是 XTier 配置：prefill 不捕获 CUDA graph（`--cuda-graph-backend-prefill disabled`，与其他三个模型相同），GPU prefill 开关照
GLM-5.3 的生产设置（BF16 Down、预解包、上传预取、路由累加）。CPU 引擎新增 GPT-OSS SwiGLU（`gate·σ(1.702·gate)·(up+1)`，钳位 7），
GPU 侧三处 Triton 内核同步支持；与 FP32 参考相对误差 1e-6（CPU）、与 CPU 引擎 1.3e-3（GPU，W4A16）。

## DeepSeek：索引器 decode 走官方的分页路径（`deepseek_v4/paged_indexer.py`）

清晨的剖析里 SM120 上索引器的 FP4 logits 和 top-k 每步 0.56 ms（生产 0.12 ms），连 gather、排序、写回一起约 1 ms。
官方的 `v41_indexer.scoring.decode_scores` 只看 `get_platform().is_sm90`：SM90 直接按请求表打分（`fp4_index_logits_paged`，持久 Triton 内核，跳过每行长度之后的块），用融合的 top-k v2 选（JIT CUDA），

`torch.topk` 选、再排序。两条路径打分用的是同一个 `_fp4_index_logits_tile`（logits 逐位相同），分页路径上没有 SM90 专用的东西

## 平台修正：SM120 的 MXFP8 GEMM 在 prefill 大小上用 128×128 tile（`xtier/platform.py`）

MiniMax 冷 prefill 的 GPU-only 剖析（2.6 万 token 一次 prefill，两个分块，每块 7.1 s）：主流忙 5.97 s，专家上传 4.09 s 在拷贝流上并行，
所以是计算受限；主流里路由专家的分组 GEMM（`_gate` + `_down`）2.89 s，MXFP8 投影 1.77 s，稀疏注意力 0.87 s。MXFP8 投影用的是
`DeviceGemmMxfp8GemmSm120 … 128_32_128`，和 decode 同一个小 N 的 tile：

- SGLang 启动时用一个 decode 形状的假 forward 给 FlashInfer 的 GEMM 做自动调优，缓存里 MXFP8 GEMM 只有 1–16 行；prefill 的调用全部
  查不到，FlashInfer 退回 tactic 0。SM120 的 CUTLASS MXFP8 有 6 个 tactic：128×32、128×64、128×128 三种 tile，各分不交换 / 交换 A、B，
  0 号就是 128×32 不交换。
- 单独计时（`xtier-dev/mxfp8_tactics.py`，按 SGLang 的方式准备 MXFP8 输入和交织的权重缩放）：

| MiniMax 的投影（K → N） | 512 行：t0 / t4 | 4096 行：t0 / t4 | 16384 行：t0 / t4 |
|---|---:|---:|---:|
| 6144 → 24576 | 0.62 / 0.40 ms | 4.63 / 3.04 ms | 29.9 / 13.2 ms |
| 8192 → 6144 | 0.24 / 0.17 ms | 1.62 / 1.04 ms | 20.5 / 4.0 ms |
| 6144 → 6144 | 0.19 / 0.13 ms | 1.21 / 0.78 ms | 7.2 / 3.1 ms |
| 3072 → 6144 | 0.12 / 0.11 ms | 0.62 / 0.40 ms | 2.4 / 1.6 ms |
| 12288 → 6144 | 0.34 / 0.22 ms | 2.36 / 1.54 ms | 33.8 / 6.0 ms |

  六个 tactic 的输出逐位相同（每种 tile 的 K 方向都按 128 分块，累加顺序一样）。32–128 行时几个 tactic 只差几个 µs、有噪声，
  256 行起 128×128 明显更快。
- 修正：钩 FlashInfer 的 `AutoTuner.choose_one`，SM120 的 CUTLASS MXFP8 在非调优模式下查不到缓存、而且至少 256 行时用 tactic 4
  （128×128 不交换）；调过的形状、调优过程和 SGLang 用 skip_ops 固定 tactic 的调用都不动（`XTIER_MXFP8_PREFILL_TILE=0` 关掉）。
  与模型无关，开不开加速包都在。

结果（MiniMax 加速包默认配置，`xtier-dev/m31_tile_test.sh`）：

- DeepSeek：官方 main 把块 FP8 当 MXFP8 的线性层都固定在 tactic 0（`pin_tactic`，SGLang 为了批次不变性用 skip_ops 跳过调优），

  照抄单 / 双并发 0/8、1/8，那 1/8 是第 1 段 3665 个字符全部抄对后多输出了一个 `</src>`（结尾停不停的平局，不是内容错误）；
  agent 两轮冷 prefill 64K 774 / 4,958（第 1 轮是启动后第一个长提示，现场编译内核）、500K 4,902 / 4,917 tok/s（分页索引器那两轮 3,196 / 5,022、4,788 / 4,793），长回复每步 31.8 ms（7 个长回复）。
