# DeepSeek V4.1 decode 一步的构成；草稿和两个请求的 FP8 投影走快内核（2026-11-11）

XTier main（v0.1.4 之后），SGLang main 27bc1a0615，单卡 RTX PRO 5000 72GB + 2× EPYC 9334（NPS4）+ 384 GiB DDR5。
DeepSeek V4.1 Flash 1017，启动台默认配置（48K 分块、每层 35 槽加弹性热专家槽、DSpark、CPU 分担 prefill）。

## 结论

- 重新剖了 decode 的一步。GPU 上的大头是热专家、FP8 投影和词表头，都已经按显存带宽在读权重（约 1.0–1.15 TB/s），
  这几项没有空间。
- 找到一处：FP8 投影的小批量快内核（FlashInfer 的 b12x）只对 1、4、6 行开。DSpark 的草稿模型一次算 5 行；两个请求同时跑时
  主模型 12 行、草稿 10 行。这几种行数都留在 CUTLASS 内核上，同样大小的 GEMM 慢 3–4 倍。
- 加速包的默认行数改成 1、4、5、6、10、12（`XTIER_MXFP8_B12X_ROWS`）：单请求每步少 0.6–0.8 ms（2–3%）；固定验证下两个请求
  同时，每步 52.3 → 44.0 ms（−16%）。只换内核，量化后的权重和激活都一样，实测两个内核的输出逐位相同。
- 变长验证（compact）的成本表按新的耗时重测了：验证 8 个以上 token 的额外成本从 22–26 ms 降到 15–18 ms。变长验证本来就靠
  少验证躲开 12 行那一档，两个请求同时的吞吐基本没变；固定验证追上来了，两种验证现在差不多（原来变长验证快 17%）。
- 4、8 个请求同时会怎样只做了估算，见最后一节。

## 一步花在哪

测法：SGLang 的 `/start_profile`，只开 GPU 活动，在一个长回答的中途录 3 秒（约 100 步）。CUDA 图回放时内核分散在几条流上
（主模型 3 条、共享专家和 hc_mix 各 1 条、草稿 2 条、热专家换入的拷贝 1 条），所以按所有流一起算墙钟时间。单请求，16K 上下文；
录的时候一步 29.4 ms，不录时 28.8 ms。

| 部分 | 每步 | 说明 |
|---|---:|---|
| 主模型 40 层：GPU 算热专家 | 11.2 ms | 每层读约 260 MB 的 MXFP4 权重（约 14 个专家），约 1.0 TB/s |
| 主模型 40 层：注意力一侧 | 8.3 ms | 每层约 160 MB 的 FP8 投影（wq_a、wq_b、wo_a、wo_b、共享专家），也按带宽在读 |
| 主模型 40 层：GPU 等 CPU 算其余专家 | 5.3 ms | 随生成的内容在 3.2–5.3 ms 之间（热专家命中率 0.59–0.69） |
| 主模型的词表头和收尾 | 1.4 ms | BF16 词表头 1.32 GB，每步读一遍（1.16 ms） |
| 草稿模型（3 层）一遍 | 3.0 ms | FP8 投影 1.41 ms（18 次调用，CUTLASS）、FP8 词表头 0.61、5 次 BF16 gemv 0.41、热专家 0.54、wo_a 0.18 |
| 两遍之间 | 0.2 ms | 采样、调度 |

- 「等 CPU」是每层 GPU 的热专家算完以后等 CPU 那部分的时间。每层调用的等待中位数 77 µs，41% 的调用等不到 40 µs
  （CPU 先算完），5% 的调用等 435 µs 以上。CPU 一侧每层约 330–350 µs（8–9 个专家），GPU 一侧约 280 µs。
- 上下文 238K 时每步多 1.2 ms：压缩注意力的索引器打分 0.13 → 0.95 ms（随上下文线性增加），热专家多 0.4 ms。
- 热专家换入的拷贝在另一条流上，每步约 1,520 次、占用 14.8 ms，和计算重叠。
- 加速包里已有的几项（wo_a 用检查点的 FP8、草稿词表头 FP8、索引器分页、Engram 提前查表）都在生效。

## 草稿和两个请求的 FP8 投影

DeepSeek V4.1 的稠密投影是 32 × 32 分块的 FP8，SGLang 在 `--fp8-gemm-backend flashinfer_cutlass` 下按 MXFP8 交给 FlashInfer。
行数很少时权重读一遍就是全部开销，加速包把 decode 的行数交给 FlashInfer 的 b12x 小批量内核（`_mxfp8_linear`），其余行数
（prefill）留在 CUTLASS。行数表原来是 1、4、6：普通 decode 和 DSpark 验证的 6 行。漏掉的是：

- 草稿模型的块：每个请求 5 行；
- 两个请求同时：主模型验证 12 行，草稿 10 行。

草稿模型的投影在服务里一次调用的 GPU 时间（trace，5 行；主模型同样形状的 6 行在 b12x 上是 39–41 µs）：

| 投影（输入 → 输出，FP8 权重） | CUTLASS（原来） | b12x（现在） |
|---|---:|---:|
| wq_b，1280 → 32768（42 MB） | 158–159 µs | 37–40 µs |
| wo_b，8192 → 5120（42 MB） | 125–128 µs | 40–41 µs |
| 共享专家 gate/up，5120 → 4608（24 MB） | 83–85 µs | 36–38 µs |
| 共享专家 down，2304 → 5120（12 MB） | 47–52 µs | 18–22 µs |
| wq_a，5120 → 1280（7 MB） | 27–31 µs | 13–17 µs |

`tests/ds_mxfp8_rows_check.py` 用同一份权重和激活对比两个内核：这五种形状、1 / 4 / 5 / 6 / 10 / 12 行的输出逐位相同（单独测时
权重留在显卡的缓存里，b12x 只要 8–25 µs，CUTLASS 27–161 µs）。

行数表仍然是一张表而不是「多少行以下」：只让 decode 图用到的宽度换内核。改成 1、4、5、6、10、12 以后（环境变量
`XTIER_MXFP8_B12X_ROWS` 可以改回去）：

| | 1、4、6 行（原来） | 1、4、5、6、10、12 行 |
|---|---:|---:|
| 草稿模型一遍（trace 里量） | 3.03 ms | 2.20 ms |
| 草稿的 18 次 FP8 投影 | 1,413 µs | 485 µs |
| 单请求每步，固定验证，同一段 1,500 token（两边都是 397 步） | 29.1 ms | 28.2 ms |
| 单请求每步，固定验证，3,000 token | 28.3 ms | 27.7 ms |
| 两个请求同时，固定验证，每步 | 52.3 ms | 44.0 ms |
| 两个请求同时：主模型一遍 / 草稿一遍（trace） | 47.8 / 3.2 ms | 41.1 / 2.4 ms |
| agent_bench 长回复每步，变长验证（各两轮） | 30.5 / 30.3 ms | 30.0 / 29.7 ms |

同一段输出两边的步数相同，草稿的接受长度没有变。各次运行生成的内容会分叉，热专家命中率和接受长度跟着变，整步时间有
2–5% 的出入，所以收益按 trace 里的内核时间和同一段输出的步数算。

## 重测变长验证的成本表

变长验证按成本表决定每个请求验证几个草稿 token（[报告](2026-11-06-ds-compact-verify.md)）。表里的耗时变了，重测一次
（`tools/sps_profile.py`，约 3 分钟），新表在 `configs/ds41-pro5000-nps4/sps-table.json`：

| | 11-06 的表 | 11-11 的表 |
|---|---:|---:|
| 每步基础 | 24.6 ms | 23.5 ms |
| 两个请求比一个多 | 1.4 ms | 1.8 ms |
| 验证 3 / 4 / 5 / 6 个 token 比 2 个多 | 1.6 / 3.2 / 4.7 / 4.3 ms | 2.0 / 3.2 / 5.1 / 3.4 ms |
| 验证 8 / 10 / 12 个 token 比 2 个多 | 21.7 / 26.3 / 24.0 ms | 14.6 / 17.9 / 15.2 ms |

超过 6 个 token 仍然贵 11–14 ms：专家这部分一次调用最多 8 个 token（`SLOT_TOKENS`），12 个 token 分成 8 + 4 两次，两次各读
一遍用到的专家。所以规划器在两个请求同时的时候还是把每个请求裁到 3 个 token 左右，合在 6 行的图里。

两个请求同时（两个 4,000 token 的长回答同时生成；采样聊天 12 题两两同时）：

| | 变长验证，原来的行数和表 | 变长验证，新行数 + 新表 | 固定验证，新行数 |
|---|---:|---:|---:|
| 每步 | 32.2 ms | 31.4 ms | 44.2 ms |
| 每个请求每步接受 | 2.6–3.1 | 2.7–2.8 | 4.0–4.2 |
| 两个长回答合计 | 179 tok/s | 175 tok/s | 184 tok/s |
| 采样聊天 12 题合计 | 161 tok/s | 165 tok/s | 154 tok/s |

变长验证两列的差别在两次运行的波动内。固定验证改之前每步 52.3 ms，同样的接受长度下两个长回答合计约 156 tok/s；现在
两种验证差不多：两个长回答固定验证快 5%，采样聊天变长验证快 7%。变长验证每步验证得少、接受得也少；固定验证每步慢，
但每步接受的 token 多，草稿容易猜对的内容（照着代码写解释）上更占便宜。

## 多个请求同时：专家按 8 个 token 分批

两个请求同时的 12 个 token 里，专家这部分分成 8 + 4 两次调用（trace 里每层两次，GPU 上各约 450 和 230 µs）。合成一次调用
可以让两次都用到的专家只读一遍。用 2026-10-20 的生产路由记录回放热专家池（每层 62 槽），加这台机器探测出的耗时模型
（GPU 33.4 + 16.74 × 专家数，CPU 32.7 + 30.06 × 专家数 + 5.88 × 路由数，µs）估算，固定验证、每个请求每步接受 3.8 个 token：

| 请求数 | 每层用到的专家（显存 / 内存） | 每步：每 8 个 token 一批 | 每步：合成一批 | 合成后合计 |
|---:|---|---:|---:|---:|
| 1 | 24（15 / 9） | 28 ms | 28 ms | 135 tok/s |
| 2 | 43（24 / 18） | 47 ms | 43 ms | 176 tok/s |
| 4 | 73（37 / 36） | 83 ms | 74 ms | 206 tok/s |
| 8 | 124（49 / 74） | 171 ms | 142 ms | 214 tok/s |

1 个请求时模型算出的专家部分是 16.1 ms，trace 里是 16.5 ms；2 个请求模型 47 ms，实测 44 ms（测试的两个请求内容相近）。
4、8 个请求里专家以外的部分按行数线性外推，误差更大。合计上不去是因为热专家池不够用：命中率 0.63 → 0.40，要 CPU 算的
专家跟着请求数翻倍，8 个请求时每步 GPU 只要 35 ms，CPU 要 117 ms。启动脚本现在是 `--max-running-requests 2`，CUDA 图只有
1、2 个请求两档。这一项没有做。

## 复现

- 两个内核的结果和耗时：`python tests/ds_mxfp8_rows_check.py`。
- 行数的影响：`XTIER_MXFP8_B12X_ROWS=1,4,6 DSPARK=1 configs/ds41-pro5000-nps4/run-ds-xtier.sh` 对不设这个变量。
- 一步的构成：服务在 decode 时 `POST /start_profile`（`{"output_dir": 绝对路径, "activities": ["GPU"]}`），几秒后
  `POST /stop_profile`，trace 里按内核名和流统计；步数用这段时间里收到的流式分片数。
- 成本表：[变长验证报告](2026-11-06-ds-compact-verify.md)里的三步。

原始数据（`bench/results/`）：`decode-step-ds41-{16k,238k}-20261111.json`（一步里各类内核的墙钟时间）、
`decode-step-ds41-16k-b12xrows-20261111.json`（加上 5 行以后）、`agent-bench-ds41-b12xrows-r{1,2}-20261111.json`（固定验证，
README 的两行）、`agent-bench-ds41-b12xrows-compact-r{1,2}-20261111.json`（变长验证，新表）、
