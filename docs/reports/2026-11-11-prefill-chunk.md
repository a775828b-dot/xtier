# DeepSeek V4.1 的 prefill 分块 22K → 48K（2026-11-11）

XTier v0.1.4（SGLang main 27bc1a0615），单卡 RTX PRO 5000 72GB + 2× EPYC 9334（NPS4）+ 384 GiB DDR5。

## 结论

- **DeepSeek V4.1**：启动台默认的 prefill 分块从 22K 改成 48K，每层热专家基础槽从 50 改成 35。冷 prefill 快 28–35%
  （agent_bench 的 500K 会话 4,893 → 6,588 tok/s），decode 每步不变（长回复 30.3 → 30.4 ms）。520K 提示、两个请求占满
  512K KV 池都实跑过，没有显存不足。
- 「Prefill 中穿插 decode」的默认挡跟着从 48 步改成 72 步：分块大了，同样的步数留给另一个请求的份额变小，72 步时它保持
  约 20% 的速度，和原来一样。
- **GLM-5.3、Qwen3.8 不改**：分块加大对它们没有收益，原因见最后两节。
- 让空闲的 CPU 分担一部分专家（`XTIER_PREFILL_CPU_SHARE=1`，启动台 DeepSeek 卡片「CPU 分担 prefill」）作为**可选项**合并，
  默认关：默认的 48K 分块下再快约 3%，22K 分块下快 7–10%，输出和关着时有微小差别。

## 为什么分块大了就快

DeepSeek 每层只有一部分专家常驻显存（热专家槽），其余在内存里由 CPU 算。prefill 时一块里有几万个 token，几乎每个专家都
被用到，所以每读一块，每一层都要把不在槽里的专家从内存传上显卡。这部分时间由专家的总大小决定，和块里有多少 token 无关。

实测每块的时间大约是 **2.5 秒（上传）+ 108 µs × token 数**。22K 的块里上传占一半；块加到 48K，同样的 2.5 秒摊给两倍多
的 token。完全不用上传时的上限约 9,200 tok/s。

## 各档分块

单个请求读冷提示（`bench/context_speed.py`，128K 取第二次读），输出 1,024 token 看 decode。全部 0 错。

| 分块 / 基础槽 | 128K 提示（tok/s） | 520K 提示（tok/s） | decode 每步 |
|---|---:|---:|---:|
| 22K / 50（原默认） | 4,776 | 4,565 | 29.1–30.8 ms |
| 28K / 46 | — | 5,133（+12%） | 29–31 ms |
| 32K / 43 | — | 5,420（+19%） | 28.7–31.1 ms |
| **48K / 35（新默认）** | **6,496（+36%）** | **5,928（+30%）** | 29.1–31.4 ms |
| 64K / 27 | 6,795（+42%） | 没测 | 30.2–30.4 ms |

选 48K 不选 64K：64K 只比 48K 再快约 5%；另一个请求的最长停顿等于一块的时间，64K 时约 10 秒；基础槽要降到 27；满上下文
没有验证。

## 显存从哪里来

一块的 forward 要的显存随 token 数增加（弹性热专家槽记下的用量：22K 约 9–10 GiB，32K 约 11 GiB，48K 13–20 GiB）。这部分从
热专家槽里让：每层少放 15 个槽（每个槽在 40 层上共 0.7 GiB）。decode 时没有大块的 forward，弹性热专家槽把这部分显存还给
热专家，补到每层 68 槽，和原来一样，所以 decode 不变。

弹性热专家关着时没有这一步，decode 只有 35 槽，会变慢。启动台在这种组合下给出提示；要关弹性，用 22K 分块配 50 槽。
启动台按分块限制槽数（48K 至多 35、32K 至多 43、22K 及以下至多 50），多选的按上限启动。「关加速包」的基线仍然是 22K 分块、
50 槽。`run-ds-xtier.sh` 自己的默认值没有改（22K、50 槽、不开弹性）。

## 两个请求时

一个请求读 227K 冷提示，另一个正在 decode（单独时约 150–158 tok/s）。`bench/interleave_probe.py`。

| 配置 | 另一个请求的速度 | 它的最长停顿 | 长提示的首字（单独 → 一起） |
|---|---|---:|---:|
| 22K 分块，48 步（v0.1.4 默认，214K 提示） | 约 22%，32–35 tok/s | 4.6–4.7 秒 | 45.4 → 57.8 秒 |
| 48K 分块，48 步 | 15%，约 23 tok/s | 7.4 秒 | 37.4 → 41.3 秒 |
| **48K 分块，72 步（新默认）** | 20%，约 32 tok/s | 7.4 秒 | 37.4 → 44.5 秒 |
| 48K 分块，72 步，484K 提示 | 21%，约 33 tok/s | 7.7 秒 | 74.3 → 96.0 秒 |

代价是另一个请求的最长停顿从 4.7 秒变成 7.4 秒（等于一块的时间）。换来的是长提示即使和别的请求一起读，也比原来单独读快。
「单独」的 37.4 秒是同一配置另一次启动里量的；72 步那次启动里它是启动后第一个长提示，带一次性开销，是 47.0 秒。

## 可选：让 CPU 分担 prefill（默认关）

prefill 时 CPU 引擎是空的。开 `XTIER_PREFILL_CPU_SHARE=1`（启动台 DeepSeek 卡片「CPU 分担 prefill」）后，一次 prefill 调用在
路由出来之后把专家块分成两份：路由少的块不上传，交给 CPU 引擎在另一个线程里同时算；其余的照常传上显卡由 GPU 算；没有 token
路由到的块两边都不算。CPU 接多少按逐次实测的成本定，让两边差不多同时算完（48K 分块实测 GPU 部分约 105 ms、CPU 部分约 90 ms
一次）。路由出来之前已经开始上传的块留在 GPU。开冷专家时不生效。

默认的 48K 分块 + 35 槽下（2026-11-11 同一天，都从启动台起）：

| 48K 分块 + 35 槽 | 关（默认） | 开 |
|---|---:|---:|
| 128K 冷提示（tok/s，各几次启动） | 6,452–6,496 | 6,643–6,685（+3%） |
| 520K 冷提示（tok/s） / 首字 | 5,928 / 87.7 秒 | 6,229 / 83.5 秒 |
| 520K 时显存峰值（共 71.7 GiB） | 68.9 GiB | 68.9 GiB |
| decode 每步（128K 提示之后 / 520K 提示之后） | 29.9–30.7 / 31.4 ms | 29.3–30.7 / 31.6 ms |
| 旁边有请求在 decode 时读 227K 冷提示：首字（单独 → 一起） | 37.4 → 44.5 秒 | 36.4 → 42.7 秒 |
| 这时另一个请求的速度 / 最长停顿 | 20% / 7.4 秒 | 21% / 7.2 秒 |
| 两个请求占满 KV 池（16K 在 decode，另一个读 48 万 token）：首字（单独 → 一起） | 74.3 → 96.0 秒 | 76.0 → 94.6 秒 |
| 这时的显存 / 错误 | 69.0 GiB / 无 | 68.9 GiB / 无 |
| 照抄（8 段，单路 / 两路） | 0–1 / 8（多的 `</src>`） | 0 / 8、0 / 8 |
| PPL（13 段 × 4K） | 3.3195 | 3.3136 |

128K 提示上开着稳定快约 3%。更长的提示单次测量互有高低（520K 快 5%，48 万 token 那次单独读慢 2%），差别和两次启动之间的波动
一样大。显存峰值不变：分担多用的约 2 GiB forward 显存由弹性热专家槽让出来。

48K 分块时一成的专家块不用上传，CPU 接 3% 的路由。22K 分块下能交给 CPU 的更多（四成的专家块不用上传，CPU 接 6% 的路由），
收益也大一些。下表是 22K 分块 + 50 槽下试过的几种做法，合并的是第一行：

| 22K 分块 + 50 槽 | 64K 提示 | 520K 提示 |
|---|---:|---:|
| 不分担 | 4,792 | 4,565 |
| **路由少的专家块整块交给 CPU（合并的这一版）** | 5,275（+10%） | 4,907（+7%） |
| 专家按路由数重排、逐个上传，CPU 和 GPU 同时算完（各约 92 ms / 层） | 5,084（+6%） | 4,797（+5%） |
| 只跳过没人路由的专家，不给 CPU | 4,211（−12%） | 4,147（−9%） |

为什么只有这么多，以及为什么默认关：

- CPU 在 prefill 里比 GPU 慢约 15 倍：同样的时间 CPU 算百分之几的路由，GPU 算其余的还带上传。收益只来自少传专家。
- 真实提示里一块 22K token 几乎用到所有专家，只有 1% 的专家块没人路由，「不传没用到的专家」没有东西可省。
- 分块越大，每个专家被用得越多，能交给 CPU 的越少：64K 分块时只多 0.4%。
- 输出和关着时不逐位一致：交给 CPU 的路由走 BF16 激活，GPU 走 MXFP8（单层相对误差 1.2e-2；同一层两条路径全部路由相比是
  4.6e-2）。整个模型上照抄 0 错，PPL 的差别在同一提示重算的摆动范围内。
- 只在 DeepSeek V4.1（MXFP4 专家、SM120 的 FP4 prefill 路径）上有这条路径，也只测了这一个模型。

单层测试 `tests/prefill_cpu_share_check.py`：分法、和 GPU 单算的误差上界、CPU 那部分在算时 GPU 调用失败后的重跑。

另外两个方向：上传槽环从 12 加到 24 / 36 没有变化；逐层 prefill（整个提示每层只传一次专家）要改 SGLang 的 DeepSeek V4
forward、注意力后端和调度分块，还和「Prefill 中穿插 decode」冲突，没有做。

## GLM-5.3：分块大小不影响速度

128K 冷提示读两次：

| 分块 / 基础槽 | prefill（tok/s） | decode 每步 |
|---|---:|---:|
| 16K / 58（默认） | 2,652 / 2,609 | 27.9 / 26.8 ms |
| 24K / 46 | 2,685 / 2,643 | 27.4 / 25.5 ms |
| 32K / 36 | 2,632 / 2,577 | 28.3 / 27.0 ms |

GLM 读一块的时间和 token 数成正比（16K 约 6.2 秒，32K 约 12.6 秒），没有 DeepSeek 那样的固定部分。它的 prefill 把专家的上传
和解包放在另外的流上和计算重叠，按这个结果看，时间花在显卡的计算上。大块还很费显存（一次 forward 16K 约 10.8 GiB，32K 约 19.7 GiB）。保持 16K、58 槽。

## Qwen3.8：现在的配置已经是最好的

128K 冷提示读两次：

| 配置 | prefill（tok/s） | decode 每步 |
|---|---:|---:|
| 默认：24K 分块，规划器布局（29 层常驻），不开弹性 | 5,290 / 5,250 | 14.65 / 14.68 ms |
| 32K 分块 | 5,304 / 5,269 | 14.63 / 14.60 ms |
| 默认 + 弹性热专家 | 5,286 / 5,211 | 14.61 / 14.56 ms |
| 显卡上少放 5.5 GiB 专家（腾给更大的分块） | 4,667 / 4,629 | 14.76 / 15.11 ms |

Qwen 七成专家常驻显卡，每块的上传只占约一成时间，分块加大摊不出什么（32K 时显存峰值 71.0 / 71.7 GiB，已经贴边）。
要给更大的分块腾显存就得少放专家，prefill 反而慢 12%，decode 也没有变快。弹性热专家开着没有差别。保持不变。
