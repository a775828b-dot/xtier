# 2026-10-23 晚：GLM / Qwen 的 512K prefill 追平生产

README 测速后，512K 冷 prefill 比生产慢：GLM 224 对 201 s（−10%），Qwen 125 对 106 s（−15%）。两个模型都跑不起生产的分块大小
（GLM 16K、Qwen 32K），先查显存，再看分块以外的差距。

## GLM：分块 16K + BF16 SSM 状态（生产参数）

图捕获之后的显存余量，生产是 10.8 GB，XTier 只有 8.0 GB。大头在 SSM 状态：SGLang 默认 FP32，生产的启动参数是
`--mamba-ssm-dtype bfloat16`，XTier 的 GLM 参数里漏了，状态缓存大了一倍（3.85 对 1.98 GB）。16K 分块原来在 KDA 线性注意力的
分块 delta 规则处显存不够；改成 BF16 状态后余量 9.89 GB，16K 分块能跑。两个参数都写进了 `configs/glm53-pro5000-nps4/run-glm-xtier.sh`
（官方 main 与加速包两行都用）。

| GLM-5.3（README 口径） | 8K 分块、FP32 状态 | 16K 分块、BF16 状态 | 生产 |
|---|---:|---:|---:|
| 加速包 64K 冷 prefill | 2389 tok/s（27.5 s） | 2803 tok/s（23.4 s） | 2386（66K，27.7 s） |
| 加速包 512K 冷 prefill | 2276 tok/s（224 s） | 2655 tok/s（192 s） | 2488（500K，201 s） |
| 加速包 64K / 512K 每步 | 28.75 / 27.46 ms | 29.27 / 27.07 ms | — |
| 官方 main（55 槽）64K / 512K prefill | 2320 / 2203 tok/s | 2663 / 2518 tok/s | — |
| PPL（加速包，13 段 × 4K） | 3.9982 | 3.9943 | 4.0598 |
| 照抄（加速包，单 / 双并发） | 1/8、0/8 | 0/8、0/8 | — |

prefill 快了 16–17%，64K 和 512K 都比生产快；decode 不变；BF16 状态没有让 PPL 变差。原始数据 `bench/results/context-glm53-*-20261023.json`。

## Qwen：PLE 层分段，32K 分块仍不够，24K 只快 2%

- 32K 分块先在 PLE 层显存不够：SGLang 对整块算 PLE 层，同时活着好几份 [token × hc_hidden] 的 BF16 张量（32K 时每份 640 MiB）。
  `packs/qwen4_exp/ple_blocks.py`（`XTIER_PLE_BLOCK`，默认 4096）对单请求的长 prefill 按 4096 个 token 一段算投影、归一化、门控和
  短卷积，卷积的跨段状态照 SGLang 的 [incoming state | chunk tokens] 布局衔接。单测 `tests/ple_blocks_check.py`：8K / 20K / 32K
  与 SGLang 逐位一致（输出、块后状态、radix 快照），32K 时峰值 7200 → 3062 MiB。
- 之后 32K 分块又在 GDN 线性注意力处显存不够。生产 Qwen 的余量是 10.24 GB，XTier 7.95 GB，差在 KV：生产是 NVFP4 KV（官方 main 的
  QSA 读不了 NVFP4，XTier 用 FP8，多占约 3 GB）。
- 24K 分块能跑：64K 冷 prefill 5268 → 5474 tok/s（+3.9%，生产 68K 5405），512K 4076 → 4160 tok/s（+2.1%，生产 4706）；decode 每步不变（14.40 / 15.54 ms）。
- 每个 24K 分块的耗时：浅处约 5 s，480K 深处约 7.5 s。固定部分约 187 µs/token，与生产短上下文时相当；随深度增长的部分 500K 全程约
  27 s，生产约 14 s。这一半差距不在分块大小。

## Qwen：QSA 索引器 prefill logits 的网格太小

同一个 450K 提示里，浅处和约 380K 深处各录了 2 个 16K 分块的 GPU 轨迹（`xtier-dev/qwen_prefill_profile.sh`）。随深度增长的几乎全是
一个 TileLang 内核（轨迹名 `kernel_kernel`）：浅处 2 块共 60 ms，深处 3389 ms；其次是 fast top-k（+195 ms）和 logits 矩阵的清零与缩放
（+260 ms）。它是 QSA 索引器 prefill 的 MQA logits（`qsa/mqa.py` 的 `tilelang_qsa_mqa_prefill`），官方 main 与生产版是同一个内核：
每个 CTA 一块查询行，顺序扫完这块行的全部压缩键。索引器按 128 MiB 的 FP32 logits 预算分行块调用它，深处有 9.5 万个压缩键（380K / 4），
一次只能放约 350 行，网格只有 11 个 CTA（GPU 有 110 个 SM），一个 16K 分块要连着启动约 47 次、12 层都是如此。

`packs/qwen4_exp/qsa_prefill.py`（`XTIER_QSA_KEYS_PER_CTA`，默认 4096）给网格加一维、按键分段，每个 CTA 只算一段键；每个 logit 仍是
同样两个操作数上一次 head_dim 的分块 GEMM、同样的 ReLU 和按头求和，缩放和 mask 照用官方的；logits 矩阵不再先清零（每行范围外的列
本来就由 mask 内核设成 −inf）。单测 `tests/qsa_prefill_check.py` 与官方结果逐位一致：

| 行 × 压缩键（对应的上下文） | 官方 | 分段 |
|---|---:|---:|
| 352 × 95088（380K） | 2.40 ms | 0.61 ms |
| 37 × 125009（500K） | 2.79 ms | 0.14 ms |
| 1000 × 25250（100K） | 0.74 ms | 0.33 ms |
| 4096 × 8524（34K） | 0.72 ms | 0.52 ms |

端到端（README 口径，24K 分块 + PLE 层分段 + QSA 按键分段，`bench/results/context-qwen38-xtier-pack-20261023.json`）：

| Qwen3.8 加速包 | 16K 分块（10-23 下午） | 24K + 两项分段 | 生产 |
|---|---:|---:|---:|
| 512K 冷 prefill | 125.1 s（4076 tok/s） | 101.8 s（5011 tok/s） | 106.2 s（4706，500K） |
| 64K 冷 prefill | 5268 tok/s | 5511 tok/s | 5405（68K） |
| decode 每步 64K / 512K | 14.34 / 15.50 ms | 14.37 / 15.57 ms | — |
| PPL（13 段 × 4K） | 3.4813 | 3.4817 | 3.4779 |
| 照抄（单 / 双并发） | 0/8、0/8 | 0/8、0/8 | — |

512K 冷 prefill 从比生产慢 15% 变成快 4%，decode 不变。官方 main 那一行仍用 16K 分块（关掉这两项分段时 PLE 层不分段）。
