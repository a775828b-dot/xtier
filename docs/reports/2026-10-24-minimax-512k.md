# 2026-10-24（下午）：MiniMax-M3.1-Flash 固定 512K 上下文（NVFP4 KV）、DSpark 按置信度截断验证

目标：MiniMax 的 KV 太占显存，改成 NVFP4，固定 512K 上下文（不做选项）；CPU 侧想办法提 decode。结果：512K 的 KV 从 FP8 的
42.5 GiB 降到 24 GiB，8 槽热专家放得下；按 agent_bench（64k 会话）冷 prefill 与 128K FP8 持平（−3%），decode 每步持平
（55.4 对 56.2 ms），tok/s −7%（截断让接受长度短了），480K 长文找数 5/5。

## 显存：FP8 KV 为什么放不下 512K

检查点的 KV 量化是 FP8（`kv_cache_quant_algo`），通用栈每 token 每层：主 K/V 4 头 × 128 × 2 × 1 字节 = 1,024，索引 K（BF16）
256，共 1,280 字节；60 层 75 KiB，加 DSpark 草稿（5 层 BF16）10 KiB。512K 要 42.5 GiB，128K 时 16 槽热专家（27.1 GiB）+ 11.3 GiB
KV 已经占满。

SGLang 给 SM100 原生栈做了 MSA-v1 NVFP4 池（`MiniMaxM3Nvfp4KVPool`）：E2M1 值、每 16 个值一个 E4M3 scale、全局 scale 1，
128 token 一页，页行 `[头, 页内槽, 字节]`，主 K/V 每 token 每层 576 字节、索引 K 72 字节，共 648 字节（FP8 的一半）。

| 512K、8 槽 | FP8（128K 池，16 槽） | NVFP4（512K 池） |
|---|---:|---:|
| 主 K/V | 7.50 GiB | 16.88 GiB |
| 索引 K | 1.88 GiB（BF16） | 2.11 GiB |
| 草稿 KV（BF16） | 1.25 GiB | 5.00 GiB |
| 热专家 | 27.1 GiB（16 槽） | 13.5 GiB（8 槽） |
| 启动后可用 | 10.3 GB | 10.5 GB |

480K 找数时显存最高 72.5 GB（共 73.4 GB，含 PyTorch 缓存的空闲块）。

## 做法（`xtier/packs/minimax_m3/kv_fp4.py`，`XTIER_MINIMAX_KV_FP4`，默认开）

- **池**：SM120 上 SGLang 的原生栈判定为假（原生栈的内核只有 SM100），池类和容量计算也跟着退回 FP8 布局。包在
  `_build_minimax_sparse_kv_pool` 和 `DefaultPoolConfigurator._compute_cell_size` 两个调用期间让判定为真，只换池类和容量；
  注意力后端和 FP8 Q 收尾仍走通用路径。池建好后把每层的 scale 视图挂到 payload 视图上（`attach_scales`）。
- **写入**：池在 SM120 上走逐缓冲区量化 + 散写（FlashInfer `nvfp4_kv_quantize`，每层约 10 个内核）。SGLang 的融合内核
  `nvfp4_store_kv_index`（主 K/V 和索引 K 一次写完）只在 SM100 上开，理由是别的架构没验证逐位一致。SM120 上验证结果：
  1–4096 token、跨步视图下两份池的字节完全相同，每层每次 260 → 6 µs。所以在 SM120 上也打开（`enable_fused_store`，
  `XTIER_MINIMAX_FP4_FUSED_STORE=0` 关）。
- **decode**：通用栈的 Triton 稀疏注意力读 FP8/BF16 缓存。这里换掉它的两个内核：索引打分与 top-k 沿用 SGLang 的分块和 top-k，
  只把打分内核换成读 NVFP4 的版本；主注意力用 split-K。两者都在寄存器里把半字节和 scale 解成 BF16（偶数维、奇数维各半块），
  一个 top-k 块（128 token）正好是一页。
- **prefill**：先把本批每个请求的上下文（主 K/V、索引 K）反量化成 BF16 临时区，每个请求连续排、配一张请求内的
  req_to_token；然后原样调用 SGLang 的 `minimax_sparse_prefill`，索引打分、top-k、跨层 top-k 复用、主注意力都用官方内核。
  E2M1 × E4M3 在 BF16 里是精确值，所以结果与在反量化缓存上跑完全相同。初版是在寄存器里解码的 prefill 内核，block_size_q = 1，
  每个查询都要把它选中的块再解一遍，64K 冷 prefill 慢了 33%（46 对 35 s）。改用临时区后每个 token 每层每块只解一次（512K 约
  1.15 GB）。临时区超过 `XTIER_MINIMAX_FP4_PREFILL_GB`（默认 1.5）时，退回寄存器内解码的内核。
- 草稿 KV 仍是 BF16（DSpark 草稿走 TRT-LLM MHA）。

## 正确性

- 内核对 SGLang 内核（同一缓存反量化后）：decode 相对 L2 ≤ 1.1e-4；索引 top-k 集合相同；prefill 新路径输出相对误差 0、
  临时区逐位相同、top-k 相同（`xtier-dev/kv_fp4_check.py`、`kv_fp4_prefill_check.py`）。
- 官方量化器（SM120 上的 FlashInfer）的输出按这里的读法解码，与 SGLang 的官方反量化逐位相同；对输入的相对误差 9.5–10%
  （随机数据）。
- SGLang 的 sparse prefill / decode 本身与稠密因果注意力对比：相对 L2 约 2e-3，> 2048 token 时块选择因果、包含本块
  （`prefill_dense_check.py`）。
- 照抄（温度 0，8 段）：NVFP4 三次的单并发是 1/8、0/8、1/8，双并发都是 0/8。两次出错都是同一个 token：第 3 段
  `tree_cache=self.tree_cache` 少了 `self.`，前两名 logit 很接近。FP8 两次都是 0/8。
- 480K 长文找数（5 个深度各一个 6 位密码）：5/5，首问冷预填充 318 s（初版内核 400 s），其余 4–5 s（命中缓存）。

## MiniMax 的 PPL 不能用来量精度

`bench/ppl_eval.py`（固定语料、裸文本）上 MiniMax 的 NLL 约 4.2（Qwen3.8 同语料 1.24），并且随位置变差，FP8 和 NVFP4 一样。
排查约两小时，依次排除了：GPU prefill 的专家（全部改走 CPU 引擎，结果一样）、稀疏注意力内核（对稠密参考 2e-3）、MXFP8 GEMM
（大 M 时逐行与单行计算相同，误差就是 MXFP8 量化的 3.8%）、M-RoPE（未启用）、DSpark 的隐状态捕获（关掉 DSpark 后
PPL 逐位相同）、输入 logprob 的算法（单位置、整段、采样路径三种算法一致）。

结论：这是模型自身的特点。它对裸文本、以及聊天里用户给的文档逐 token 预测都很差：每段前加文档开头 token `]~!b[` 后 4.1，
放进聊天模板仍是 6.1，源码 8.2。但它在聊天里表现正常：短问答全对，3K token 源码后的问题答对（它指出给的代码只有 import），
照抄和找数也都过。所以 MiniMax 的精度对比用照抄和找数。`ppl_eval.py` 加了 `--prefix`（每段前加不计分的文本），这次带
`]~!b[` 测得 NVFP4 4.163、FP8 4.108，只作相对参考。

|---|---:|---:|---:|---:|

| 官方代码 + 必要修正：NVFP4 512K、8 槽、草稿 7、不截断（启动台「关加速包」） | 1,824 / 1,883 | 45.9 | 3.86 | 84.1 ms |
| FP8 128K、16 槽（之前的默认，今天复测） | 1,900 / 1,953 | 55.5 | 3.12 | 56.2 ms |
| NVFP4 128K、16 槽（初版内核） | 1,431 / 1,476 | 54.0 | 3.35 | 62.0 ms |
| NVFP4 512K、8 槽（初版内核） | 1,439 / 1,482 | 45.3 | 3.21 | 70.7 ms |

## DSpark 按置信度截断验证（`xtier/packs/speculative/dspark_truncate.py`，`XTIER_DSPARK_TRUNCATE`）

MiniMax 的 DSpark 草稿带一个置信度头：对每个草稿 token，预测在前缀都被接受的条件下它被接受的概率。SGLang 只在 ragged verify
模式下构建这个头，M3.1 的 NVFP4 又要求 static，所以默认没有。这里在 static 下也构建它。

- **规则**：每个请求保留生存概率（各位置置信度的累乘）≥ 阈值的前导草稿，至少保留 1 个。保留 k 个时验证封顶在 k + 1 行，
  做法与 SGLang 的 cap-accept 模式相同：static 收尾的图内贪心接受读 `verify_lens_buf`，采样接受图和图外接受拿它当 cutoff，
  所以被截掉的草稿不论主模型算出什么都判为拒绝。这一步输出的就是一个 k token 草稿块的结果，无损。
- **省 CPU**：被截掉的行通过 XTier 的 decode 路径 token 标志跳过路由专家。注意力是因果的，这些行既不影响保留的行，也不影响
  接受判断；在混合 MoE 上，省下的主要是 CPU 专家。
- **模拟**：用 SGLang 的 STS 采集（`SGLANG_DSPARK_STS_COLLECT_PATH`，每个验证步记录原始置信度和贪心接受前缀）收了一轮 agent
  和照抄，共 3,020 个验证步。置信度头校准得很好：agent 部分平均接受 2.51 个，预测 2.57。按“CPU 专家数随验证行数增长”的模型估算，
  阈值 0.2 / 0.3 / 0.5 的 agent decode 分别 +12.5% / +14.8% / +16.5%。
- **实测**（阈值 0.3）：照抄单 / 双并发都是 0/8；agent decode 45.3 → 50.4 tok/s（+11%），每步 70.7 → 56.5 ms，CPU 每层
  798 → 493 µs，每层不同的 CPU 专家 16.2 → 10.5 个，接受长度 3.21 → 2.85。启动脚本默认 0.3，启动台「关加速包」时关掉。

## 草稿长度（γ）

同一份 STS 数据：固定 γ = 4 / 3 的 agent decode 估计 +0.1% / −0.8%（截断把短草稿的好处都拿到了，而且按请求、按步自适应），
所以维持 5。

## 下一步

  按窗口的紧凑草稿缓存，DSpark 没有；移植过来可以无损省下约 5 GiB，相当于多 3 个槽。
