# 第 2 步：Qwen3.8 与 GLM-5.3 跑在官方 SGLang main 上（2026-10-23）

官方 SGLang main `8cd3c494` + XTier（插件，不改官方源码），对照生产管线 lsglang_q3.8fn（lkqmoe 0.5.6 + LKQstrata，10-22 基线）。
同一台机器：RTX PRO 5000 72GB + 2× EPYC 9334，NPS4（8 个 NUMA 节点），112 个 CPU 专家线程。

| PPL（13 段 × 4096，固定语料） | **3.4769**（NLL 1.24615） | 3.4779（NLL 1.24644） |
| 照抄测试（8 段代码，单请求 / 2 并发） | 0/8、0/8 | 0/8、0/8 |

- 每个验证步慢 1.5%（门槛 2% 以内），接受长度更高，解码总速度快 2.7%；短提示 prefill 比生产快，4K 慢 2%、8K 慢 6%；精度与生产一致。

- 最终配置：生产同款缓存布局、MTP 草稿的 MoE 也交给 XTier（全常驻 W4A16，`XTIER_DRAFT=1`）、hc_mix 重叠内核（`packs/qwen4_exp`）。

  验证步数取自 `/metrics`）；并发用生产基线同一个 `conc_bench.py`；prefill 用 `bench/ttft_probe.py`（token ids，每次先清前缀缓存，
  取 3 次中位数）；照抄用 `bench/copy_test.py`。原始数据在 `bench/results/*-20261023.json`。
- 未测：512K 召回（需要 NVFP4 KV 与 512K 上下文，下一步核对官方是否支持）。

## 怎么接进官方 SGLang

官方 `FusedMoE.__init__` 在创建任何权重之前会问一次 `create_kt_config_from_server_args`（KTransformers 混合推理的入口），
拿到配置就把检查点自己的 MoE 方法包成 `KTEPWrapperMethod`。XTier 的插件只做两件事：
对规划器选中的层回答一个 XTier 的层配置，并把这个包装类换成一个子类，遇到 XTier 配置时构造 `XTierMoEMethod`
（真正的 KTransformers 配置保持原样）。模型加载完有自检：本该接管的层没接管就报错，不会悄悄退回官方路径。

- **权重**：按检查点 MoE 方法自己的布局（参数名、形状、加载器）建在主机内存；某一层最后一个专家张量加载完，
  立刻交给 CPU 引擎（按 NUMA 节点切分复制），主机参数原地释放。官方加载器在后处理时会把整层参数临时搬到 GPU，
  交接之后那里只剩空参数，什么也不会搬。
- **解码**：每 8 个 token 一个信箱槽：GPU 内核把输入写进映射内存，流内存操作把请求交给 CPU 调度线程并等待，
  再读回结果；可以被 CUDA 图捕获。缓存命中的专家在 GPU 上算（W4A16），与 CPU 并行，最后相加。
- **prefill**：四条路径——
  1. 全部专家常驻的层：新写的分块内核直接在缓存槽的 FP4 权重上算（硬件 FP4→FP16 解码，与解码内核同一套算法）。
     比"拷贝 + 整层解包成 BF16"快 2–7 倍：单层 m=100 2.1 ms、m=4096 7.8 ms、m=16384 24.8 ms（原路径 14–47 ms）。
  2. 部分缓存的层，< 2560 token：混合——命中缓存的路由用同一套分块内核在槽上算，其余同时在 CPU 上算，FP32 相加。
  3. 部分缓存的层，更长：移植的 0.5.6 GPU prefill（从锁页的 NUMA 分片按块上传，分组 GEMM，跨层预取）。
  4. 没有缓存的层：≥ 1024 token 同 3，否则 CPU 引擎同步计算。
- **热专家缓存**（`xtier/cache`）：LKQstrata 的移植，每层槽数可以不同；全部常驻的层不经过 CPU 和信箱。
  按生产布局配置：生产的 25 个 GPU 常驻层全部常驻，另外 23 层各 155 个槽，用生产的排名画像，共 42.1 GiB。

## 官方 main 在这台机器上遇到的问题

| 问题 | 处理 |
|---|---|
| Qwen PLE 的 n-gram 嵌入表（2000 万 × 2560 FP8，47.7 GiB）用缓存分配器锁页，向上取整到 64 GiB 且落在一个 NUMA 节点，NPS4 下永远分配不完 | `packs/qwen4_exp`：精确大小的匿名映射，交错到 8 个节点后注册给 CUDA（约 20 秒） |
| TileLang 0.1.12 先试 HIP：机器上装着 ROCm（`/opt/rocm/bin/hipcc`，没有 AMD 卡），QSA 索引器内核按 ROCm 编译失败 | `xtier/platform.py`：CUDA 版 torch 时先问 CUDA 检测器 |
| transformers 5.19 读这个检查点的分词器只得到 33 个 token（目录里没有 tokenizer.json） | 用 5.12 另存一份带 tokenizer.json 的分词器（编码逐 token 一致），`--tokenizer-path` 指过去 |
| pip 装了 nvcc 13.4，运行时头文件是 13.0，JIT 编译报"编译器与头文件不兼容" | 编译器包降到 13.0.88（与生产一致） |
| 服务预热请求在 Qwen VL 处理器里越界 | `--skip-server-warmup`，待查 |
| 官方 hc_mix 内核先清零累加区再过两次全局栅栏 | `packs/qwen4_exp`：生产的重叠内核（每步 −1.8%） |
| 官方默认把 prefill 也捕获成 CUDA 图 | `--cuda-graph-backend-prefill disabled`（与生产相同） |
| `XTIER_MAIN_CPUS=auto` 把 JIT 编译限制在 15 个 CPU 上，FlashInfer MoE 首次编译要 40 分钟 | 单独用全部 CPU 编一次（2 分钟，之后走缓存） |

## GLM-5.3 Flash（同一晚的冒烟测试）

不改 XTier 的后端，只加了 `packs/glm5_next` 的两项修正（见下），GLM-5.3 Flash NVFP4 就在官方 main 上跑起来了：
42 个 MoE 层全部由 XTier 接管，每层 60 个热专家槽（生产画像，33.2 GiB），注意力用 TileLang 的 DSA 后端。

| 项目 | XTier | 生产 |
|---|---|---|
| PPL（13 段 × 4096） | **3.9869** | 4.0598（生产 prefill 把注意力 / MLP 换成了 W8A8） |
| 解码，EAGLE（`conc_bench.py`，512 token，温度 1.0） | 单请求 64.7 tok/s（接受 2.40），2 并发合计 89.7 tok/s（2.30） | 82.3 tok/s（2.54），112.4 tok/s（2.54） |
| 解码（不开投机） | 单请求 45.9 tok/s，2 并发合计 76.3 tok/s | — |
| 热专家命中率 | 0.52–0.54（自适应换入换出在工作） | — |

- 按每步算慢约 20%：CPU 专家部分与生产同一个引擎，差距在 GPU 侧——DSA 用的是 TileLang 后端（生产是 FlashInfer sparse MLA + kpool 补丁），
  没有生产的 mHC 融合、小批 GEMM 等补丁，也没开拒绝采样（官方要求草稿与目标词表相同，生产用 49152 的草稿词表）。

- 检查点把注意力投影按拆开的名字列为不量化（`*.self_attn.q_proj` 等），官方加载时是融合的 `qkv_proj`，排除判断只认 MLA 的几个名字：
  融合层的所有子层都在列表里时视为不量化（通用修正，可提给官方）。
- 生产用的 FlashInfer sparse MLA 后端只放行 GLM-5 的架构名；放行后又因为 GLM-5.3 的 DSA 用了 kpool（`index_kpool > 1`）、
  这个后端的解码还不支持而失败，所以用 TileLang 后端（生产里这部分是补丁）。
- EAGLE：官方 `DeepseekModelNextN` 遇到 `modelopt_fp4` 就把草稿的量化配置置空（DeepSeek 的 NVFP4 检查点 NextN 层是 BF16），
  GLM-5.3 的 NextN 专家却是 NVFP4；包里让 GLM-5.3 草稿跳过这个判断，草稿的 MoE 也交给 XTier 全常驻。

## DeepSeek V4.1 1017

- MXFP4 格式已适配（官方把 UE8M0 块缩放存成 FP32 的 2 的幂，取回指数字节），`tests/formats_check.py` 在真实层上逐字节一致。
- 还不能端到端：检查点里 Engram 表 189 GB、专家 276 GB，官方 main 只有主机内存的 Engram 表，两者加起来超过整机 377 GB。
  需要先把生产的 Engram NVMe 行存储（`adapter/engram_backend.py`、`row_store.cpp`）做成 `packs/deepseek_v4`。

## 差距与下一步

- 长提示 prefill：部分缓存层每个分块都要整层上传（约 27–29 ms/层，受 PCIe 限制），所以分块要大。32K 上下文配置（显存比例 0.85）
  改用 32K 分块后，30K token 首 token 5.31 s（约 5650 tok/s，生产 33K token 5879 tok/s）；512K 配置（0.90）在 32K 分块时
  官方的 PLE 短卷积显存不够，只能 16K。跳过已缓存专家会把每块上传切成很多段（每段 48 次拷贝），不划算。
- 解码每步还慢 1.5%：待逐层剖析（官方 main 的注意力等非 MoE 部分与生产补丁不同）。
- Qwen：QSA 下的 NVFP4 KV（生产补丁移成包）、32K 分块的显存。
- GLM：kpool 下的 FlashInfer sparse MLA、mHC 融合、草稿词表下的拒绝采样（都是生产补丁，逐项移成 `packs/glm5_next`）。
- DeepSeek：Engram NVMe 行存储包，然后核对 DSpark、1017 检查点适配等生产改动。
- 规划器：用画像里的路由计数在全局显存预算下分配槽位，代替照搬生产的"整层常驻 + 每层固定槽数"。
