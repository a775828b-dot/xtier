# 长 prefill 进行时让另一个请求继续 decode（2026-11-10，v0.1.4）

## 现象

SGLang 调度时 prefill 优先。一个请求在读长提示（分块 prefill）时，另一个正在 decode 的请求拿不到 decode 步，要等整段提示读完。
实测（RTX PRO 5000，启动台默认配置，另一个请求先单独 decode 12 秒，再发一个冷的长提示）：

| 模型 | 冷提示 | 另一个请求的 decode | 最长一次停顿 |
|---|---:|---|---:|
| DeepSeek V4.1 | 214K token，首字 45.4 秒 | 34.6 步/秒 → 0.44 步/秒 | 40.3 秒 |
| GLM-5.3 | 119K token，首字 47.0 秒 | 33.6 → 0.28 | 40.5 秒 |
| Qwen3.8 | 211K token，首字 41.7 秒 | 70.6 → 0.94 | 36.6 秒 |

## 做法

SGLang 自带 `--prefill-decode-interval N`（默认关）：每读完一块 prefill，先跑 N 轮 decode，再读下一块。没有请求在 decode 时不生效，
单个请求的速度不变。XTier 没有改调度，只做了两件事：

- 启动台加选项「Prefill 中穿插 decode」（`xtier/console/core.py` `interleave_option`），**默认开**，默认挡是让另一个请求保留约两成速度的那一档
  （DeepSeek 48 步、GLM 64 步、Qwen 96 步）。一块 prefill 的耗时和一步 decode 的耗时各模型不同，所以每个模型的挡位（N）不同，选项文字里写了
  实测的效果。直接用 `configs/*/run-*.sh` 起服务时自己加 `--prefill-decode-interval N`。
- 弹性热专家槽（`XTIER_CACHE_ELASTIC`）在一个提示的两块之间不再加槽。原来的规则是「连续 32 次 decode 前向后加槽」，N 大于 32 时每块之间都会
  加槽，下一块 prefill 前又全部释放：DeepSeek V4.1、N = 150 时十块 prefill 每块都释放并重新上传 8.4 GiB。现在 prefill 前向的 token 数达到分块
  大小（`--chunked-prefill-size`）时，认为这个提示还有下一块，之后要连续 `XTIER_CACHE_ELASTIC_IDLE_CHUNK`（1024）次 decode 前向才加槽；
  提示的最后一块通常不满一块，照旧按 32 次。测试 `tests/elastic_chunk_check.py`。

## 各挡实测

另一个请求（A）单独 decode 的速度：DeepSeek 143 tok/s，GLM 94 tok/s，Qwen 184 tok/s。「A 的速度」是长提示在读期间的速度。

| 模型 | 每块插几步 | A 的速度 | A 的最长停顿 | 长提示首字 |
|---|---:|---:|---:|---:|
| DeepSeek V4.1 | 关 | 约 2 tok/s | 40.3 秒 | 45.4 秒 |
| | 16 | 约 14 tok/s | 4.6 秒 | 48.9 秒（+8%） |
| | 48 | 约 32 tok/s | 4.7 秒 | 57.8 秒（+27%） |
| | 150 | 约 67 tok/s | 4.6 秒 | 84.6 秒（+86%） |
| GLM-5.3 | 关 | 约 1 tok/s | 40.5 秒 | 47.0 秒 |
| | 64 | 约 21 tok/s | 6.3 秒 | 60.0 秒（+28%） |
| Qwen3.8 | 关 | 约 2 tok/s | 36.6 秒 | 41.7 秒 |
| | 96 | 约 40 tok/s | 4.9 秒 | 52.5 秒（+26%） |

- 两头是线性的交换：A 拿到的时间份额越大，长提示读得越慢。三个模型的中间挡（48 / 64 / 96 步）都是 A 保持约 22% 的速度，长提示首字晚 26–28%。
- 最长停顿等于一块 prefill 的时间（DeepSeek 22K token 约 4.6 秒，GLM 16K 约 6.2 秒，Qwen 24K 约 4.6 秒），和 N 无关。要更短只能减小分块。
- GLM 的 24、192 步和 Qwen 的 36、288 步没有单独测，选项文字里的数是按实测的「每步代价」（GLM 27.7 ms，Qwen 13.1 ms）折算的，标了「估」。
- DeepSeek 的 48、150 步两档是带弹性槽修正测的；修正前是 59.3 秒 / 85.4 秒，A 的速度几乎相同（7.59 对 7.79、16.04 对 16.17 步/秒）。
  修正省掉的主要是每块之间的 8.4 GiB 上传。

## 怎么测

`bench/interleave_probe.py`：先单独发一个冷的长提示，再让请求 A 流式输出、12 秒后发第二个冷的长提示，统计 A 的流式块（每个 decode 步一块）
在之前、期间、之后的速率和期间最长的间隔。间隔是服务启动参数，每个挡位启动一次服务。

```bash
python bench/interleave_probe.py --port 18190 --model DeepSeek-V4.1-Flash-1017 --tokens 200000
```

另外测了一个只为长提示加的预热（启动后第一次读整块 prefill、第一次带工具定义的请求各多花多少），结论是不需要：DeepSeek 第一次读 36K token
提示多 3.0 秒，GLM 第一次带工具定义的请求多 3.5 秒，Qwen 都在 0.5 秒以内，启动台现有的三条预热已经覆盖了主要的首次开销。

## 默认挡的回归

用默认挡（DeepSeek 48 步、GLM 64 步、Qwen 96 步）起服务，另一个客户端连续读 4 个冷的长提示（DeepSeek / Qwen 各 21 万 token，GLM 12 万），
同时跑单路照抄；读完后再跑两路照抄。

| 模型 | 长提示在读时的单路照抄 | 两路照抄 | 弹性槽 | 服务日志里的错误 |
|---|---|---|---|---|
| DeepSeek V4.1 | 4 轮：1、0、1、0 段有差别（都是下面说的那一种） | 0 / 8 | 只在每个长提示的开头释放 | 0 |
| GLM-5.3 | 0 / 8 | 0 / 8 | 同上（4 个长提示释放 3 次，每次 16 槽 8.9 GiB） | 0 |
| Qwen3.8 | 0 / 8 | 0 / 8 | 默认没开 | 0 |

DeepSeek 有差别的每次都是第 2 段的同一处：3,665 个字符的正文一致，末尾多一个 `</src>`（提示里包住原文的结束标签）。它和穿插无关：
不带长提示的照抄 3 轮是 0、1、1；v0.1.3 的代码、不加这个参数连跑 5 轮是 1、1、0、1、0；10-28 以来保存的 57 份 DeepSeek 照抄结果里有 13 份
是这一种，没有别的差别。是模型在这一段结尾「停下」和「再写一个结束标签」之间的临界选择。看 DeepSeek 的照抄结果时要看差别的内容，这一种不算回归。
