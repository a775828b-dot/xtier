# 2026-10-24（晚）：自动规划器第一版（PLAN 第 3 步）

目标：热专家怎么分层放（哪些层全常驻、其余每层几个槽）不再手调，由规划器按"每层 CPU 和 GPU 同时算完"自动定，验收线是
不差于手调的生产配置。结果：

- 规划器由探测（本机 × 层形状的 GPU / CPU 耗时系数，约 1–3 分钟）、耗时模型、全局预算动态规划三部分组成，可以离线出方案
  （`tools/plan_auto.py`），也可以启动时现算（`XTIER_CACHE_PLAN=auto`）。用法见 [docs/planner.md](../planner.md)。
- 模型经实测校准：自适应换入让槽位"等效放大"（DS 1.69、GLM 1.47、MiniMax 2.19、Qwen 约 1.4–1.6）；GLM 的 CPU 侧模型 300 µs 对
  日志实测 288 µs；单层探测比真实服务每次信箱调用少约 28 µs，补上后 Qwen 五组布局差的预测误差 0.08 ms。
  用静态档案（不计自适应）算出的 Qwen "最快方案"实测反而慢 0.8%、64K prefill 慢 4.4%，计入后模型预测与实测方向一致。
- Qwen：启动时自动规划（v2 探测）给出 29 层全常驻 + 18 层 64–88 槽（同显存，手工是 26 + 22 × 155），agent_bench 两轮：
  五个会话冷 prefill 快 2.4–2.9%，decode 每步在手工的 +0.6% 以内，达到验收线。
  让 CPU 多分担（所有层部分缓存，热专家显存从 41.7 降到 13.7 GiB）实测每步慢 3.3%、prefill 慢 14%，不划算；模型在离手工布局远的
  方案上不准，所以启动时规划默认只在手工布局附近挪动。
- GLM / DeepSeek：两者都受 CPU 限制，各层偏斜接近，规划器的不均匀分槽预测只快约 0.4–0.5% 每步（GLM 实测 −0.2%，在噪声边缘），低于 1% 的保护门槛，现在保留均匀分槽。
  真正的杠杆是显存（模型：GLM 每多 1 GiB 热专家 decode 约快 1%），但 GLM 512K prefill 时显存已用满，要拿分块或预取深度换；
  换入节奏改成 DS 的每 2 窗 32 个，GLM 每步实测 −0.7%（建议改默认）。
- MiniMax：各层差别小，同显存下均匀 8 槽就是最优；显存峰值只剩 0.75 GiB，没有加槽的余地。

## 组成

| 部分 | 文件 | 作用 |
|---|---|---|
| 探测 | `xtier/planner/probe.py`、`tools/plan_probe.py` | 按层形状造合成权重（随机 FP4 码、scale 为 1；内核速度与数值无关，不要检查点），走 XTier 自己的解码路径（信箱、CUDA 图）测 GPU 算 n 个命中专家、CPU 算 n 个专家 / r 个路由、部分缓存层两边同时算，以及 prefill 上传带宽。每张图 32 次调用、每次换一组路由（权重从显存 / 内存读，和真实 decode 一致） |
| 耗时模型 | `xtier/planner/cost.py` | 每层一次调用：全常驻 gpu(n)；部分缓存 E[max(gpu(n_g)+p0, cpu(n_c, r_c)+p1)]；不缓存 cpu(n, r)。n、r 来自路由档案（每个专家被多少窗口用到、多少 token 路由到它），max 的期望用 Clark 公式；自适应换入让 S 个槽命中得像档案前 adapt×S 名 |
| 优化 | `xtier/planner/auto.py` | 全局槽位预算下按层动态规划（槽数步长 E/64），最小化 decode + λ·prefill 上传；默认（`KEEP`）在 decode 不超过手工布局、上传不多于手工布局的方案里取上传最少的（关掉 KEEP 时界限是最快方案 ×(1+tol)），λ 先网格后二分；预测收益 <1% 且上传不减少时保留手工布局。约 1 秒 |
| 启动时规划 | `xtier/planner/__init__.py`、`auto.from_env` | `XTIER_CACHE_PLAN=auto` + `XTIER_PLANNER_PROBE`；预算默认 = 启动脚本的手工布局（同显存）；日志一行 `xtier planner:` |
| 档案 | `tools/plan_trace.py` | `XTIER_ROUTE_TRACE` 记录 → 带 counts、routes 的档案（GLM 原档案没有 counts，MiniMax 没有档案） |
| 校准 | `tools/plan_calibrate.py` | 运行日志的 `XTier cache:` 行 → 自适应系数，并核对 CPU 侧 |
| 检查 | `tests/planner_check.py` | 不用 GPU：Clark 公式对抽样、预算、不差于均匀分、λ 单调、`from_env` |

原来的 `xtier/planner/budget.py` + `tools/plan_cache.py`（只按"CPU 少读几个专家"贪心分槽）删掉：它给 Qwen 的方案是 47 层全部
部分缓存、没有全常驻层，prefill 每块要多传 25 层；这类方案实测（Qwen 一节末尾）每步慢 3.3%、prefill 慢 14%。

## 探测（本机：RTX PRO 5000 + 2×Genoa ES NPS4，112 专家线程）

| 层形状 | 每次 token | GPU：g0 + g1·n | CPU：c0 + c1·n + c2·r | 部分缓存 p0 / p1（误差） | 上传 |
|---|---:|---|---|---|---:|
| Qwen3.8：512 × 2560 × 640 NVFP4，top-10 | 4 | 19.4 + 2.17 n（1.27 TB/s） | 16.3 + 5.01 n + 1.00 r（+ 0.79 µs / token；v1 只按专家数：52.9 + 5.67 n） | +7.5 / −3（6.4 µs） | 56.4 GB/s |
| GLM-5.3：288 × 4096 × 2048 NVFP4，top-8 | 4 | 26.7 + 11.87 n（1.19 TB/s） | 27.5 + 24.06 n + 3.85 r（每专家 588 GB/s） | +9 / −2（9.0 µs） | 57.4 GB/s |
| DS V4.1：384 × 5120 × 2304 MXFP4，top-6 | 6 | 33.4 + 16.74 n（1.12 TB/s） | 32.7 + 30.06 n + 5.88 r | +6 / −5.5（18.2 µs） | 57.5 GB/s |
| MiniMax M3.1：128 × 6144 × 3072 NVFP4，top-4 | 6 | 38.1 + 27.39 n（1.16 TB/s） | 32.9 + 48.68 n + 17.13 r | +11 / −3.5（32.9 µs） | 57.5 GB/s |

- GPU 部分每用到一个专家读一次（与 token 数无关），约 1.1–1.2 TB/s；CPU 每个专家的读取已到内存带宽（GLM 588 GB/s，本机实测上限约 590）。
- CPU 还要按路由（token-专家对）付计算：GLM 每个路由 3.85 µs，约是读一次专家（24 µs）的 1/6；MiniMax 专家更大，计算占主导（同样 32 个路由，
  4 个专家 1,012 µs、32 个专家 2,172 µs）。第一版探测（v1）只按专家数拟合，部分缓存层误差 GLM 18.6 µs、MiniMax 226 µs；加路由项（v2）后 GLM 9.0、MiniMax 32.9 µs。
- 信箱往返 + 引擎每次调用的固定开销约 20–35 µs（v1 把路由的计算并进了常数，Qwen 显得是 53 µs）。Qwen 两版都上机验了（下文）：
  在手工布局附近两版都和实测一致，v2 在"全部层部分缓存"这一端判错，见 Qwen 一节末尾。

**让 CPU 多分担？**（10-22 提过的想法）v2 探测把 CPU 侧每次调用的固定开销测成 20 µs（v1 是 53 µs，把路由的计算并进了常数），
按它算，所有层都留部分缓存、只用 13.7 GiB 热专家时 decode 最快（预测每窗口 −0.2 ms，约每步 −1.4%）。实测（短提示 + 64K）：

| Qwen3.8 | 热专家 | 显存峰值 | 短提示每步 | 64K 冷 prefill | 64K 每步 |
|---|---|---:|---:|---:|---:|
| r26 手工 | 26 全常驻 + 22 × 155 | 71.4 GB | 13.833 ms | 5,442 | 14.44 ms |
| 全部部分缓存（v2 的最快方案） | 第 0 层全常驻 + 47 × 88–144 | 42.7 GB | 14.29 ms（+3.3%） | 4,682（−14%） | 14.74 ms |

decode 反而慢 3.3%，模型判错了方向；prefill 慢 14% 在预料之中（多传 25 层）。推测原因：探测是一层反复调用，真实解码里 47 个
不同的层轮流走信箱，每次调用的固定开销（调度线程切换、各层的数据结构不在缓存里）比探测测到的大；v1 的常数偏大反而接近这种情况
（v1 + 1.6 对这组预测 +0.8%，方向对、量偏小）。所以 Qwen 不该让 CPU 多分担：省下的 28.7 GB 显存只有在另有用途（更长上下文、更多
并发）时才值得每步 +3%、prefill −14% 的代价。

因此启动时规划默认"decode 不差于手工布局、上传不多于手工布局"（`XTIER_PLANNER_KEEP=1`），只在手工布局附近挪动，那里两版探测都和
实测一致；`XTIER_PLANNER_KEEP=0` 才按"最快方案"放开。

**偏差排查与校准**（23 点以后补做）：
- 不是调度线程扫描槽位：同一层上额外注册 512 个闲置信箱槽位，部分缓存调用 72 → 71 µs，不变（`xtier-dev/planner_slots_exp.py`）。
- 不是每个 token 的开销：v3 探测把路由数和"有 CPU 路由的 token 数"分开变化，每个 token 只多 0.8 µs（v2 的路由项其实混进了
  token 数，但两者都小）。v3 系数 cpu = 16.3 + 5.01 n + 1.00 r + 0.79 t µs。
- 不是自适应统计的锁：调度线程更新热度时用 try_lock，策略线程持锁时直接丢掉这次统计，不阻塞。
- 不是多层切换：8 个独立的层轮流调用（各自的引擎数据、信箱、缓存），每次只多 5 µs（`planner_layers_exp.py`）。
- 不是主线程 CPU 上的忙等：在本进程的主线程 CPU（专家线程的 SMT 兄弟核）上跑 1–4 个独立的忙等进程，每次调用 +0.1 µs。
  （用 Python 线程忙等时每次 +52 µs，但那是抢 GIL 拖慢了发图的主线程，探测本身的假象。）
- 还没排除：真实解码里两次 MoE 调用之间隔着几百微秒的注意力等 GPU 计算，专家线程和调度线程不是背靠背被调用（唤醒、缓存状态）；
  下一步在服务里直接给信箱往返计时。
- 关掉自适应换入做对照（`XTIER_CACHE_ADAPT=0`，模型不需要自适应系数）：

| Qwen3.8，关自适应 | 短提示每步 | 64K 冷 prefill | 64K 每步 |
|---|---:|---:|---:|
| r26 手工 | 14.038 ms（开自适应 13.833） | 5,431 | 14.43 ms |
| 全部部分缓存 | 15.103 ms（+1.065） | 4,675 | 15.83 ms |

  三版探测的预测：v1 +0.93、v2 +0.50、v3 +0.26 ms——单层探测少算了每次经信箱调用的开销。用这一对加开自适应的几组联合标定：
  **v3 探测 + 每次信箱调用多 28 µs（`--call-us` / `XTIER_PLANNER_CALL_US`）+ 自适应系数 1.4**，五组差值的预测误差 0.08 ms（rms）：

| 差（短提示每步） | 预测 | 实测 |
|---|---:|---:|
| 关自适应：全部部分缓存 − r26 | +1.150 ms | +1.065 |
| r26：开 − 关自适应 | −0.151 | −0.205 |
| 开自适应：静态最快方案 − r26 | +0.040 | +0.106 |
| 开自适应：全部部分缓存 − r26 | +0.454 | +0.457 |

  28 µs 的来源没查到（见上面排除的几项）。校准后的模型对 agent 测到的两个方案：27 层方案 decode +0.6%、prefill +1.1%，与实测一致；29 层方案 decode
  预测 +2.75%，agent 实测只有 +0.5%（各会话 +0.3–0.6%）。所以离手工布局远时模型仍有约 2% 的误差，默认的 KEEP 是必要的；`LAYOUT=auto`
  用的是 agent 实测过的 v2 方案。原始数据 `bench/results/planner-20261024/{verify,context}-qwen-{r26static,v2faststatic,v2fast}.json`、
  `probe3-qwen38-112t-m4.json`。

## GLM-5.3

路由档案：手工布局（每层 60 槽）跑 verify_step_bench + 64K 时开 `XTIER_ROUTE_TRACE`，`plan_trace.py` 得到 42 层 × 288 专家、
14,274 个解码窗口（每窗口 18.1–26.2 个不同专家，均值 21.0；前几层多、后面少）。同一次运行的缓存日志：命中 0.517、每次 20.7 个专家、
CPU 288 µs；档案前 60 名只覆盖 0.388，自适应系数 1.47；模型按测得的命中算 CPU 侧 300 µs，对实测 288 µs。

同显存（2,520 槽）的规划：所有层都是 CPU 侧更慢（CPU 270–470 µs、GPU 150–200 µs），规划器把槽从后面的层（每窗口约 19 个专家）
挪到前面的层（约 25 个、分布更平）：前 9 层 80 槽、中后层 48 槽，预测 MoE 每窗口 13.651 → 13.547 ms（−0.8%，约每步 −0.4%）。

| GLM-5.3（EAGLE，每层 60 槽 / 方案 48–80 槽） | 短提示每步 | 64K 冷 prefill | 64K 每步 | 全程命中 / CPU 每次 |
|---|---:|---:|---:|---:|
| 手工（均匀 60） | 26.745 ms | 2,774 tok/s | 28.08 ms | 0.517 / 288 µs |
| 规划（不均匀） | 26.695 ms | 2,735 | 29.07 | 0.512 / 294 µs |

实测没有收益（短提示 −0.2% 在噪声内；64K 每步 GLM 开了自适应草稿步数，本身有 ±5% 的波动；全程 CPU 时间反而 +2%）。逐层模型
预测不了这么小的差别（可能各层的自适应收益不同），所以加了最小收益保护：方案不减少上传、预测收益又不到 1% 时保留手工布局。
现在规划器对 GLM 同显存给出的就是均匀 60 槽。DeepSeek 离线同样（每层 32–72 槽对均匀 50，预测 −0.9% MoE / −0.5% 每步），没上机。

手工布局重复测了一次（加 510K），短提示每步 26.745 / 26.735 ms，重复性约 ±0.04%；按这个精度，规划方案的 26.695 ms（−0.2%）
可能是真实的小收益（预测 −0.4%），但远小于保护规则的 1% 门槛，所以默认仍保留均匀分槽。

**显存**：模型算出 GLM 每多 1 GiB 热专家（约 76 槽，每层多 1.8 个）MoE 每窗口约 −0.28 ms（约每步 −1%）。但 512K 冷 prefill 时
显存峰值 72,824 / 73,415 MiB（nvidia-smi，含 PyTorch 缓存），留 1.5 GiB 余量后没有可加的（实验脚本因此跳过了加槽那次运行）。
启动后、CUDA 图之后报的可用 9.87 GB 基本都被 16K 分块的 prefill（12 块预取的打包权重约 2.7 GB、BF16 解包、注意力）用掉。
所以 GLM 想多放热专家，只能拿 prefill 的分块大小或预取深度换——这是规划器下一步要建模的取舍（需要 prefill 显存和速度随分块的模型）。

**换入节奏**：GLM 启动脚本用的是默认的每 4 窗换一次、每次最多 16 个；DS（生产）和 MiniMax 用每 2 窗、32 个。GLM 换成后者：

| GLM-5.3（每层 60 槽） | 短提示每步 | decode | 64K 冷 prefill | 运行时命中 | 自适应系数 | CPU 每次 |
|---|---:|---:|---:|---:|---:|---:|
| 默认 4 / 16（两次） | 26.745 / 26.735 ms | 93.9 / 94.0 tok/s | 2,774 / 2,736 | 0.517 / 0.514 | 1.47 | 288 / 290 µs |
| 2 / 32 | **26.559 ms（−0.7%）** | 95.1 | 2,739 | 0.533 | 1.54 | 280 µs |

零成本的小收益（模型按系数 1.47 → 1.54 预测约 −1.5%，方向对、量偏大）。启动脚本的默认值没改，建议改成 2 / 32（与 DS、MiniMax 一致）。
CPU 侧模型核对：实测每次 9.7 个 CPU 专家，模型 291 µs，日志 280 µs。

512K 冷 prefill 2,658 tok/s、510K 每步 26.55 ms（手工布局，供参考）。原始数据 `bench/results/planner-20261024/{verify,context}-glm-*.json`。

## 结论与下一步

- **显存预算自动化**：现在预算取手工布局（同显存）或给定值。GLM / MiniMax 在最长 prefill 时显存已用满，Qwen 峰值还剩约 2 GiB。
  下一步要把 prefill 分块、预取深度、KV 池的显存和速度建进模型，才能在"多放热专家（decode）"和"大分块 / 深预取（prefill）"之间
  自动取舍；测法可以沿用今晚的：最长 prefill 时采显存峰值（`planner_ab.sh` 的 `*.gpumem`）。
- **CPU 线程、prefill 分块**：仍是启动脚本的值；线程数要在不同进程里探测（引擎线程池按进程固定）。
- **自适应系数在线测**：`XTier cache:` 日志只在第一个经信箱的层打印（Qwen 第 0 层全常驻所以没有），改成按层统计后可以直接求每层的
  系数（GLM 不均匀分槽没兑现，可能就是各层系数不同）。
- **档案**：GLM、MiniMax 的档案取自今晚的短提示 + 64K 负载；用 agent 负载重采更贴近 dsh。
- **建议改的默认值（未改）**：GLM 换入节奏 2 / 32（每步 −0.7%）；Qwen 用 `LAYOUT=auto`（v2 探测，agent 冷 prefill +2.4–2.9%，decode 持平）。
- **每次信箱调用的现场开销**：单层探测比真实服务少约 28 µs / 次（已作为 `call_us` 校准，来源未定位）。下一步让探测轮换多个层、
  并在主线程忙等的情况下测，或在服务里直接计时信箱往返；之后再放开 `XTIER_PLANNER_KEEP=0` 的远离手工布局的方案。
