# 2026-10-25：用提示的路由预热热专家池；两个启动报错

目标：热专家池（自适应换入）只看 decode 窗口的路由，新请求开头的几十个窗口里，池子还是上一个请求的专家。Strata 0.2.4 在提示读完后
用提示的路由预热（`cache_settle`）。10-20 的 DeepSeek 生产路由记录推算：请求前 50 个窗口命中 0.47–0.57（稳定后 0.63），占全部窗口
的 32%，若开头就有稳定命中率，decode 最多快 4.3%（短回复 10.7%）。结果：

- 预热后每一段窗口的命中率都提高（请求前 5 个窗口 0.556 → 0.593，整体 0.565 → 0.574），CPU 每次少算 1–8% 的专家；
  窗口时间 32.94 → 32.49 ms（−1.4%）。不改变输出。
- 请求开头窗口慢主要不是 Engram：多出的 1.6 ms 里 1.4 ms 在 CPU（池子还是上一个请求的专家、换入和 CPU 抢内存带宽）。调参复测：每轮 64 次、分 8 轮最好，长提示后前 5 个窗口 35.26 → 33.79 ms；但开预热时索引层在开头各多约 0.3 ms，原因待查。
- 默认关（`XTIER_CACHE_PROMPT=1` 打开）。稳态的自适应换入本身每轮都满额（约 18 GB/s），也在和 CPU 抢内存带宽，见“调参复测”。

## 做法

- prefill 时，每个部分缓存的层在 GPU 上数这次提示里每个专家被选中的次数（`index_add_`，不同步）；最后一个部分缓存的层把计数拷到
  锁页内存，在流上挂一个主机回调交给信箱的策略线程（`xtier/cache/pool.py record_prompt`、`csrc/mailbox` 的 `xtier_mailbox_pool_prompt`）。
  DeepSeek 开着 decoder replay（第 20 层以后只算提示的最后一块），所以长提示只交接一次，前面各块的计数在 GPU 上累加。
- 策略线程把提示的计数按 `XTIER_CACHE_PROMPT_WINDOWS`（10）个 decode 窗口的量并入专家热度（原热度 × `XTIER_CACHE_PROMPT_KEEP`
  0.7），从下一个 decode 窗口起跑 `XTIER_CACHE_PROMPT_ROUNDS`（4）轮、每轮最多 `XTIER_CACHE_PROMPT_SWAPS`（256）次换入。

## 调参复测（10-25 晚）

问题：开头那几个约 34 ms 的窗口为什么慢（是不是 Engram 未命中）；换小批量、分多轮换入能否少抢带宽。四组同样各两轮 agent_bench
（`xtier-dev/tp-sim/ab-warm2.log`，路由记录 `trace-warm{0,1,128,64}.bin`）。

长提示之后（前面空了 3 s 以上）的窗口，命中率 / CPU 每次算的专家 / 窗口时间：

| 配置 | 第 0–5 个窗口 | 第 5–10 个 | 第 10–25 个 |
|---|---|---|---|
| 不预热 | 0.539 / 10.33 / 35.26 ms | 0.519 / 11.09 / 34.27 ms | 0.469 / 12.65 / 35.30 ms |
| 每轮 256 × 4 轮 | 0.608 / 8.92 / 34.49 ms | 0.556 / 10.11 / 33.64 ms | 0.503 / 11.94 / 33.87 ms |
| 每轮 128 × 4 轮 | 0.597 / 9.13 / 35.01 ms | 0.553 / 10.27 / 34.23 ms | 0.497 / 12.04 / 34.49 ms |
| 每轮 64 × 8 轮 | 0.623 / 8.57 / 33.79 ms | 0.565 / 9.96 / 33.10 ms | 0.504 / 11.84 / 33.84 ms |

每个请求的前 5 个窗口对第 50 个以后（`layer_gaps.py`：逐层 CPU 调用之间的间隔、CPU 引擎时间）：

| 配置 | 窗口 前 5 / 50 以后 | CPU 时间 前 5 / 50 以后 |
|---|---|---|
| 不预热 | 34.25 / 32.66 ms | 16.45 / 15.05 ms |
| 256 × 4 | 34.27 / 31.67 ms | 15.70 / 14.68 ms |
| 128 × 4 | 34.75 / 31.96 ms | 16.16 / 15.15 ms |
| 64 × 8 | 33.86 / 31.33 ms | 15.00 / 14.76 ms |

- 开头慢主要不是 Engram：第 13→14 层（第二个 Engram 层）只多 0.13 ms。不预热时多出的 1.6 ms 里 1.4 ms 在 CPU：池子里还是上一个
  请求的热专家，新请求开头命中低，同时换入在抢内存带宽（每个专家的 CPU 时间也高）。
- 小批量多轮（64 × 8）最好：前 5 个窗口的 CPU 额外时间 1.40 → 0.24 ms，长提示后第 0–5 个窗口 35.26 → 33.79 ms。每轮 128 × 4 没有改善。
- 但所有开预热的配置，前 5 个窗口里进入索引层（第 20/24/28/32/36 层：`index_source_layer_ids` 中压缩比为 1、索引器扫全部上下文的几层）
  之前的间隔各多约 0.3 ms（共 1.3–1.7 ms），不预热时没有。原因待查（换入写显存和这几层抢显存带宽 / L2？）。
- 稳态的换入本身就满额：不预热时 239,205 次换入 / 3,742 轮 = 每轮 63.9 次（上限 `XTIER_CACHE_EVERY` 2 × `XTIER_CACHE_SWAPS` 32），
  即 decode 时约每 2 个窗口 1.2 GB（约 18 GB/s）。窗口按 2 拍交替（`swap_beat.py`）：除索引层外的层间隔奇偶差 1.68 ms（打乱后 0.64），
  CPU 时间奇偶差 1.31 ms（打乱后 0.73）——上传的那一拍 CPU 专家变慢，换入从主机内存的专家分片读，和 CPU 引擎抢内存带宽。
- 两次运行的输出不同（采样），各组第 50 个窗口以后的基线差约 ±0.7 ms，绝对窗口时间的比较要打折；命中率和 CPU 专家数受影响小。
- 下一步：降低稳态换入量的 A/B；预热改为从 prefill 已经上传到显卡的专家做显存内拷贝（不再从主机读）。

## 两个启动报错

- MiniMax 包（`xtier/packs/minimax_m3`）在官方 main 上给 `model_config.uses_minimax_m3_nvfp4_native_stack` 挂钩子，这个函数只有
  M3.1 分支有，每个进程都报一条 "Failed to apply hooks"。现在按文件检查 M3.1 分支，没有就不挂任何钩子（M3.1 环境照旧 11 个）。
- 带 `--skip-server-warmup` 时，SGLang 的预热线程在 uvicorn 监听端口之前就 POST `/freeze_gc`，连接被拒（每次启动 2 条 Traceback），
  GC 冻结也没生效。`xtier/platform.py` 在服务进程里等端口能连上再让它发（`XTIER_FREEZE_GC_WAIT_S`，最多 120 s）。
