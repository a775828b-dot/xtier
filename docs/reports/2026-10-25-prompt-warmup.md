# 2026-10-25：用提示的路由预热热专家池；两个启动报错

目标：热专家池（自适应换入）只看 decode 窗口的路由，新请求开头的几十个窗口里，池子还是上一个请求的专家。Strata 0.2.4 在提示读完后
用提示的路由预热（`cache_settle`）。10-20 的 DeepSeek 生产路由记录推算：请求前 50 个窗口命中 0.47–0.57（稳定后 0.63），占全部窗口
的 32%，若开头就有稳定命中率，decode 最多快 4.3%（短回复 10.7%）。结果：

- 预热后每一段窗口的命中率都提高（请求前 5 个窗口 0.556 → 0.593，整体 0.565 → 0.574），CPU 每次少算 1–8% 的专家；
  窗口时间 32.94 → 32.49 ms（−1.4%）。不改变输出。
- 请求开头 10 个窗口的时间没变（开与不开都约 34 ms），另有瓶颈；预热的集中换入让 CPU 算每个专家慢 2–4%（拷贝和 CPU 抢内存带宽）。
- 默认关（`XTIER_CACHE_PROMPT=1` 打开），待查开头窗口的瓶颈、调换入批量后再定。

## 做法

- prefill 时，每个部分缓存的层在 GPU 上数这次提示里每个专家被选中的次数（`index_add_`，不同步）；最后一个部分缓存的层把计数拷到
  锁页内存，在流上挂一个主机回调交给信箱的策略线程（`xtier/cache/pool.py record_prompt`、`csrc/mailbox` 的 `xtier_mailbox_pool_prompt`）。
  DeepSeek 开着 decoder replay（第 20 层以后只算提示的最后一块），所以长提示只交接一次，前面各块的计数在 GPU 上累加。
- 策略线程把提示的计数按 `XTIER_CACHE_PROMPT_WINDOWS`（10）个 decode 窗口的量并入专家热度（原热度 × `XTIER_CACHE_PROMPT_KEEP`
  0.7），从下一个 decode 窗口起跑 `XTIER_CACHE_PROMPT_ROUNDS`（4）轮、每轮最多 `XTIER_CACHE_PROMPT_SWAPS`（256）次换入。

## 两个启动报错

- MiniMax 包（`xtier/packs/minimax_m3`）在官方 main 上给 `model_config.uses_minimax_m3_nvfp4_native_stack` 挂钩子，这个函数只有
  M3.1 分支有，每个进程都报一条 "Failed to apply hooks"。现在按文件检查 M3.1 分支，没有就不挂任何钩子（M3.1 环境照旧 11 个）。
- 带 `--skip-server-warmup` 时，SGLang 的预热线程在 uvicorn 监听端口之前就 POST `/freeze_gc`，连接被拒（每次启动 2 条 Traceback），
  GC 冻结也没生效。`xtier/platform.py` 在服务进程里等端口能连上再让它发（`XTIER_FREEZE_GC_WAIT_S`，最多 120 s）。
