# Kimi K3.1 Pro 实验（2026-11-05）

分支 `kimi-k31`，基于 v0.1.1（4b1e766），**不合进 main**。2.8T 参数的 Kimi K3.1 Pro 在测试机上能跑通：默认配置（尾部跳过 R = 9）代码题 decode 每秒约 10 个 token，prefill 约 90 tok/s。离日常使用还差得远，这里作为实验记录和参考。

## 结论

- **能跑**：96K 上下文，2 个并发。每层 896 个路由专家里有 78% 只在 NVMe 上，模型文件里的专家字节已经打洞删掉，只存一份。
- **瓶颈是读盘**：decode 每步要从盘上读几百到两千个冷专家，每个 17.5 MB。所以下面三项提速都是在减少读盘时间：
  1. 加两块盘：+14%。
  2. DFlash2：代码题每步平均接受 4.2–4.7 个 token，共 +25%。
  3. 尾部跳过：R = 9 时开 DFlash2 的代码题 4.94 → 10.31 tok/s（约 2.1 倍），**会改变输出**。把不跳过当作原版（好比 Q8），R = 9 相当于 Q5_K_M 和 Q4_K_M 之间（见"精度"一节）。
- **GPU 热专家几乎不帮忙**：热专家在 GPU 上，也同时在内存里。多放只省 CPU 计算，不减少读盘。每层从 4 个加到 17 个，只快 2.7%。
- **prefill 卡在上传**：每块 prefill 都要把整层专家传上 GPU，约 90 tok/s，和盘无关。

## 测试机

| 部件 | 型号 |
|---|---|
| CPU 和内存 | 2× EPYC 9334（64 核 128 线程），384 GiB DDR5 24 通道，NPS4（8 个 NUMA 节点） |
| GPU | RTX PRO 5000 72GB（SM120） |
| 冷存储 | 4× Samsung 9100 PRO 1TB（PCIe 5.0 x4）+ 2× P5800X 400GB（PCIe 4.0 x4） |

## 准备和启动

1. **下载两样东西**：
   - `moonshotai/Kimi-K3.1-Pro`：路由专家是 MXFP4 QAT，共 1347 GiB，其余是 BF16。
   - DFlash2 草稿模型 `RadixArk/Kimi-K3.1-Dflash2-Preview`。
2. **SGLang 用分支**：Kimi K3.1 的支持在 `kimi-k3.1-support` 分支（accf045c83，11-04 的 main 加一个提交），不在 main 上。
3. **非专家投影转成 4 bit**：`python tools/kimi_mxfp4_dense.py SRC DST`。
   - 默认转成 NVFP4，潜投影保留 BF16，下文叫 **NVD**。
   - 加 `--latent` 连潜投影也转，叫 **NVD-L**。它省 6.2 GiB 显存、约快 4%，但精度更差（见下文"精度"一节）。
4. **第一次启动写冷存储**：用 `XTIER_COLD=1` 启动，会把 92 层专家写进冷存储，约 16 分钟。
5. **只存一份**：`python tools/cold_punch.py MODEL_DIR --paths ...` 把模型文件里的专家打洞删掉，只留冷存储这一份。
6. **（可选）换到更多盘**：`python tools/cold_relayout.py --key OLD --paths ... --new-key NEW --new-paths ... --units 3 --parts 5:5:5:5:2:2`。
   - 每条记录读出来、写进新布局、再读回来逐字节比对，1347 GiB 用了 443 s。
   - 旧存储不改，确认新存储能正常启动后再删。
7. **启动**：`configs/kimi-k31-pro5000-nps4/run-kimi-xtier.sh`。路径是测试机的，用之前改成自己的。
   - 脚本里设了 `PYTHONSAFEPATH=1`。如果工作目录下有 SGLang 源码目录，`python -m` 会把 `sglang` 当成那个目录的命名空间包，SGLang 自己的 `__init__` 不执行。
   - 不设的后果：缓存不重定向，FlashInfer 和 Triton 要重新编译；GPU 还会多占约 1.2 GiB，弹性热专家少一档，代码题 decode 从 10.31 掉到 9.92 tok/s。测试机的启动台就是这种情况。

## 这个分支加了什么

| 部分 | 改动 |
|---|---|
| CPU 引擎 | top-k 最多 16，每层专家最多 1024 个；SiTU-GLU 激活（CPU 引擎和三个 Triton 内核） |
| 专家格式 | 支持 SGLang 的 `Mxfp4MoEMethod`（compressed-tensors MXFP4）。建模型时 GPU 方法用 `torch.zeros` 建主机参数，92 层一共会提交 1.4 TB 内存，这里改成不初始化 |
| `xtier/packs/kimi_k3` | SM120 上的 DSA：<br>• FlashMLA 没有 SM120 版本，改走 Triton；<br>• BLOCK_K 按共享内存大小定；<br>• 超过 16 个头的长 prefill 走 split-K。<br>另外负责 4 bit 非专家变体的参数改名、丢掉 BF16 原件 |
| 冷存储分段（`XTIER_COLD_UNITS=3`） | 每个节点份再切 3 段（gate、up、其余），`XTIER_COLD_PARTS` 按盘速分配，例如 `5:5:5:5:2:2`。原来只能整份分配，6 块盘分 8 份最好也只有 2:2:1:1:1:1，速度一点不变 |
| 尾部跳过（`XTIER_TAIL_SKIP=R`，默认关） | 参考 Strata 的 `STRATA_ROUTE_TAIL_SKIP`。<br>• 规则：一次 decode 或单请求验证窗口里，不在内存的专家，如果每个 token 都把它排在第 R 名以后（0 是权重最大），就不读、不算，其余专家不重新归一化。<br>• `XTIER_TAIL_SKIP_EVAL=1`：在 prompt 里按每个 token 模拟同样的规则，用来测精度。<br>• Kimi 的配置里默认开 R = 9 |
| 启动台条目 | `configs/kimi-k31-pro5000-nps4/console.py`：默认值就是上面的测试配置，可选 DFlash2 开关、尾部跳过 R = 9 / 10 / 11 / 关 |
| 弹性热专家 | 紧急检查先清分配器缓存再判断。原来开 DFlash2、保留量 0.5 GiB 时，每步的临时显存会触发紧急线，加出来的槽全部被收回 |
| 测量工具 | `bench/ppl_eval.py --top N` 导出每个位置最可能的 N 个 token；`bench/kl_compare.py` 算两次之间的 KL、首位 token 改变比例、NLL 差 |

## 测速

- **题目**：三道代码题：Python 写新代码、Python 改代码（输出大部分照抄原文件）、TypeScript 写新代码。
- **测法**：关思考，贪心解码；先跑三道不同长度的热身题，再测，只算首个 token 之后的时间；合计 = 三题总 token 数 ÷ 三题总 decode 时间。脚本 `kimi_code_bench.py`。
- **共同配置**：96K 上下文，KDA 状态缓存 8 份，KV 用 FP8（SGLang 的 DSA 池没有 NVFP4 布局），8K 一块 prefill，每层 22% 的专家在内存里。

| 配置 | 代码题 decode | 每步读冷专家 |
|---|---|---|
| NVD，4 块盘，不开 DFlash2（16 份状态缓存、64K，起点） | 3.73 tok/s | 362–438 |
| NVD-L，4 块盘，不开 DFlash2 | 3.83 tok/s | 359–426 |
| NVD-L，6 块盘（加傲腾，分 3 段） | 4.35 tok/s | 359–424（读盘每步 0.160 → 0.126 s） |
| NVD-L，6 块盘，尾部跳过 R = 11 | 6.10 tok/s | 199–242 |
| NVD-L，6 块盘，DFlash2 块宽 5 | 5.41 tok/s | 1959–2158 |
| NVD-L，6 块盘，DFlash2 块宽 5，尾部跳过 R = 11 | 8.66 tok/s | 962–1061 |
| NVD，6 块盘，DFlash2 块宽 5，不跳过 | 4.94 tok/s | 1972–2083 |
| NVD，6 块盘，DFlash2 块宽 5，尾部跳过 R = 11 | 8.29 tok/s | 931–1081 |
| NVD，6 块盘，DFlash2 块宽 5，尾部跳过 R = 10 | 9.36 tok/s | 852–973 |
| **NVD，6 块盘，DFlash2 块宽 5，尾部跳过 R = 9（默认配置）** | **10.31 tok/s** | 700–859 |

- **开 DFlash2 时**：弹性热专家的保留量要 2 GiB（XTier 默认）。DFlash2 每步有些步骤不在 CUDA 图里，会临时占用显存。
- **12K 提示词的 prefill**：
  - 4 块盘时 95.7 tok/s，6 块盘时 90.8 tok/s。
  - 每块 prefill 几乎把冷专家整个读一遍，再把整层专家传上 GPU。4K 一块时卡在上传，8K 一块时上传和 GPU 计算一起卡，盘反而在等它们。
- **照抄测试**（2 段）：R = 11、10、9 都是 0 处出错。

## 精度

- **测法**：
  - `bench/ppl_eval.py` 给 13 段 4K 文本打分（英文文档 6 段、agent 对话 6 段、中文 1 段），每个位置导出最可能的 20 个 token；`bench/kl_compare.py` 拿它和不跳过的 NVD 比。
  - 尾部跳过用 `XTIER_TAIL_SKIP_EVAL=1` 在 prompt 里逐 token 模拟；哪些专家在内存里，按代码题记下的路由固定（`XTIER_CACHE_PROFILE`）。
  - 这样测比实际 decode 偏保守：实际开 DFlash2 时，要验证窗口里每个 token 都把专家排在 R 名以后才跳，而且 prompt 本身不跳。
  - 同样的权重重跑一次，NLL 只差 0.0001–0.0004，下表的差别都在这之上。

| 配置 | 代码题 decode | NLL 差（PPL） | KL 均值 / p99 | 首位 token 改变 | 贪心命中 |
|---|---|---|---|---|---|
| NVD，不跳过（基准） | 4.94 tok/s | 0（3.156） | — | — | 72.69% |
| NVD-L，不跳过 | 5.41 tok/s | +0.0087（+0.9%） | 0.014 / 0.13 | 5.4% | 72.51% |
| NVD，R = 11 | 8.29 tok/s | +0.0083（+0.8%） | 0.015 / 0.13 | 5.7% | 72.47% |
| NVD-L，R = 11 | 8.66 tok/s | +0.0162（+1.6%） | 0.024 / 0.21 | 7.1% | 72.36% |
| NVD，R = 10 | 9.36 tok/s | +0.0104（+1.0%） | 0.019 / 0.17 | 6.4% | 72.42% |
| NVD，R = 9 | 10.31 tok/s | +0.0151（+1.5%） | 0.024 / 0.21 | 7.2% | 72.28% |

- 代码题 decode 都是 6 块盘、DFlash2 块宽 5。贪心命中是最可能的 token 正好等于原文下一个 token 的比例。
- **直观对比**：把不跳过当作原版（好比 Q8），R = 9 相当于 Q5_K_M 和 Q4_K_M 之间。依据是 llama.cpp perplexity 文档里 Llama 3 8B 各量化相对 FP16 的 KL：Q8_0 0.0014、Q6_K 0.0055、Q5_K_M 0.011、Q4_K_M 0.031。R = 9 是 0.024，R = 11 是 0.015，接近 Q5_K_M。模型不同，只能粗比。
- **NVD-L 不划算**：它本身的损失和 R = 11 差不多；NVD-L 加 R = 11 的损失又和 NVD 加 R = 9 差不多，后者快 19%。
- **首位 token 改变多在模型本来就拿不准的位置**：这些位置上，基准首位 token 概率的中位数只有 0.25，超过 0.8 的不到 1%。
- **中文损失大一些**：尾部跳过时，中文那段的 KL 是英文的 1.4–1.5 倍（只有 1 段，仅供参考）。

## 已知限制

- **KV 只能 FP8**：SGLang 的 DSA 池只有 FP8 布局，96K 时 KV 一共 1.7 GiB，换成 NVFP4 也只省约 0.5 GiB。
- **DFlash2 的两个要求**：草稿模型的滑窗 MLA 只能走 Triton（`--speculative-draft-attention-backend triton`）；要 `--mem-fraction-static 0.92`，KV 池才分得到显存。
- **冷存储没有冗余**：打洞以后它是专家唯一的一份，6 块盘坏任何一块都要重新下载模型。
- **尾部跳过会改变输出**：贪心解码时，在接近平局的位置会选到别的 token。R 越小省的读盘越多，损失也越大。
