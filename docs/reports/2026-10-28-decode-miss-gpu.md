# 2026-10-28：decode 未命中的专家交给 GPU 代算（可选，默认关）

问题：decode 时热专家池没命中的专家全由 CPU 算，GPU 算完命中的专家就等 CPU。CPU 弱的机器（核少、只有 AVX2、内存带宽有富余）
等得更久，这时把一部分未命中专家的权重经 PCIe 拷进显存、交给 GPU 算，可以把 GPU 的空闲填上。本机（2×EPYC 9334，24 通道）
CPU 读内存约 470 GB/s，PCIe 5.0 拷贝约 50 GB/s，CPU 算一个专家比 PCIe 拷一个快 8 倍左右，所以这里做成选项、默认关，
收益要在 CPU 弱的机器上实测。

## 做法（`XTIER_DECODE_MISS_GPU=比例`，`xtier/cache/pool.py`）

- 每次 decode 调用（一个信箱槽，最多 8 个 token）打包之后，GPU 上一个小内核（`_miss_select`）从这次未命中的 n 个专家里取
  round(比例 × n) 个（最多 `XTIER_DECODE_MISS_GPU_MAX` 个，默认 8），路由多的先取，一样多取 id 小的：GPU 这边一个专家的代价
  基本是拷它的权重，和 token 数无关，CPU 那边 token 越多越费时。
- 取走的路由在交给 CPU 的那份里改成 −1（和命中的专家一样，CPU 引擎跳过），GPU 一侧排在命中专家之后。
- 权重从 CPU 引擎锁页的 NUMA 分片拷进显存暂存区（`_miss_copy`），由 SM 直接读主机内存：CUDA 图里拷贝引擎的拷贝地址是固定的，
  跟不上 GPU 上才选出来的专家。实测 SM 连续读 50–53 GB/s，和拷贝引擎（50 GB/s）一样；在计算内核里按行直接读主机内存只有
  22–24 GB/s（每行一次只读 128 字节），所以先拷进暂存区再算。
- 计算用热专家池原来的 `_gate_up` / `_down`，加了一个编译期开关（槽位换成暂存区、序号从表里读），最后照旧按路由顺序合并、
  加上 CPU 的结果。所以 GPU 代算的专家和命中的专家结果逐位相同。
- 暂存区所有层共用（各层依次执行），大小 = 上限 × 一个专家（DeepSeek 8 × 17.9 MiB = 143 MiB），和热专家槽一起在 KV 缓存
  之前分配。
- 冷专家层不开（冷专家的内存槽在一次前向里会被换掉）；没有引擎分片时（`XTIER_PREFILL_FROM_SHARDS=0`）也不开。
- 日志里热专家池的 hit 会把 GPU 代算的专家也算进去（CPU 调度器按“GPU 算了哪些”统计）。
- 启动台：DeepSeek、GLM、Qwen 三张卡加了「未命中专家 GPU 代算」（关 / 10% / 20% / 30% / 50%，默认关；关加速包、开冷专家时变灰）。

## 核对

- `tests/miss_gpu_check.py`：四个模型各取一层真实权重（GLM-5.3 NVFP4；Qwen3.8 NVFP4，每个 NUMA 节点 80 行，验证分片边界；
  DeepSeek V4.1 MXFP4；MiniMax M3.1 GPT-OSS SwiGLU），m = 1–8、比例 1 / 0.5 / 0.3、即时执行和 CUDA 图重放、带跳过的 token：
  - 取走的专家与主机上按同样规则算的一致；
  - 输出与“把取走的专家放进热专家池”的那一层逐位相同（比例 1 时与全部常驻的层逐位相同）；
  - 与只用 CPU 引擎的结果相比，相对误差 ≤ 1.7e-3（与命中的专家同量级）。
  四个模型全部通过。
- 关着时：`_gate_up` / `_down` 在 DeepSeek、GLM 两种形状下生成的 PTX 与改动前相同（只差调试信息里的路径和行号）；
  `tests/cache_check.py` 通过。
- 端到端：照抄测试（`bench/copy_test.py`，8 段，单请求 / 两请求）见下表，GLM-5.3、Qwen3.8 开 30% 也都是 0/8。
  第 2 段以没闭合的 `dict(` 结尾，DeepSeek 抄完偶尔多输出一个 `</src>`（表中 *）：关着也会出现（8 线程关的两次；10-23、10-24
  没有这个功能的 5 次照抄，同一位置、同样的 7 个字符），是数值稍有变化就翻的收尾，与 GPU 代算无关；其余各段全部 0 差异。

## 结果（DeepSeek V4.1 Flash 1017，启动台默认配置，RTX PRO 5000 + 2×EPYC 9334）

CPU 弱的机器用 CPU 专家线程数模拟：16 线程（CPU 一层慢约 3 倍）、8 线程（每个 NUMA 节点 1 个，慢约 6 倍）。decode 速度取
照抄 600 词那题（各配置输出的文字相同，token 数一样，可以直接比）；CPU 每层耗时是热专家池日志的两段（每段 500 个窗口）。

| CPU 专家线程 | 代算比例 | 照抄 单 / 两请求 | decode tok/s | CPU 每层每次（µs） |
|---|---|---|---:|---|
| 112（本机实测配置） | 关 | 0/8 / 0/8 | 102.3 | 327 / 223 |
| 112 | 10% | 1/8* / 0/8 | 90.8（−11%） | 294 / 203 |
| 112 | 30% | 0/8 / 0/8 | 66.1（−35%） | 244 / 164 |
| 16 | 关 | 0/8 / 0/8 | 84.5 | 1014 / 687 |
| 16 | 10% | 1/8* / 0/8 | 84.3（持平） | 865 / 553 |
| 16 | 30% | 0/8 / 0/8 | 65.5（−22%） | 726 / 454 |
| 8 | 关 | 1/8* / 1/8* | 65.0 | 1857 / 1193 |
| 8 | 10% | 0/8 / 0/8 | 68.7（+6%） | 1637 / 1058 |
| 8 | 20% | 0/8 / 0/8 | 69.8（+7%） | 1474 / 960 |

写一段 147 token 的代码那题（各配置输出相同的那几组）：112 线程 154.5 → 107.6（10%）；16 线程 60.2 → 73.5（10%，+22%）；
8 线程 37.3 → 42.8（10%，+15%）→ 46.0（20%，+23%）。

- 本机 CPU 算一个 DeepSeek 专家约 30–40 µs，GPU 拷一个约 380 µs（17.9 MiB，50 GB/s），交出去越多越慢。CPU 慢到算一个专家要
  一两百 µs 时开始有收益。
- 比例取多少：每层 CPU 和 GPU 各自的时间都会变，最好的比例约为（CPU 一层的时间 − GPU 一层的时间）÷（CPU 算一个 + GPU 拷一个）
  ÷ 每次的未命中数；比例太大时 GPU 一侧反过来成瓶颈（16 线程 30%）。建议从 10% 试起，看 decode 每步时间。
- 这里的模拟是核少、内存带宽有富余的情况：PCIe 拷贝读的也是同一组内存，CPU 已经把内存带宽读满的机器（例如核多的双通道
  台式机），交出去的那部分 CPU 也省不下来。PCIe 4.0 的机器拷一个专家的时间要翻倍。
