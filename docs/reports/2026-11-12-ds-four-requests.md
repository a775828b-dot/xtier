# DeepSeek V4.1：同时跑 4 个请求（2026-11-12，v0.1.5）

RTX PRO 5000 72 GB + 2×EPYC 9334（NPS4，112 线程）。DeepSeek V4.1 Flash 1017，加速包、DSpark、512K 上下文，启动台默认参数
（48K 分块、35 槽 + 弹性热专家）。服务都从启动台起，每组一次启动。

## 改了什么

| | 原来 | 现在 |
|---|---|---|
| 同时处理的请求（`--max-running-requests`） | 2 | 4 |
| KV 池（`--max-total-tokens`，启动台用 `KV_POOL` 给） | 512K token，和上下文一样 | 1M token；单个请求的上下文上限仍是 512K |
| 一次专家调用最多的 token（`XTIER_SLOT_TOKENS`，三个模型都一样） | 8 | 16 |
| DSpark 验证（启动台默认） | 固定：每个请求每步验 6 个 token | 变长：按成本表决定验几个（成本表测到 4 个请求），再补满到图的档位 |
| 走小批量快内核的 FP8 投影行数（`XTIER_MXFP8_B12X_ROWS`） | 1、4、5、6、10、12 | 1–24 |

起因是 agent 会派子 agent。原来第 3 个请求要排队；KV 池只有一个上下文那么大，子 agent 读进来的内容会把主会话的缓存挤掉，
主会话回来要重读；多个请求同时 decode 时每个都慢得多。

- **4 个请求同时**：每步 48.8–49.8 ms，合计 251–254 tok/s，每个 57–67 tok/s。改之前最多 2 个同时，合计约 175 tok/s；
  只把上限放到 4、别的不改是每步 81 ms、合计约 200 tok/s。
- **2 个请求同时**：每步 38.1–39.0 ms，合计 191–197 tok/s（原来 45 ms、约 175 tok/s）。
- **只有一个请求时不变**：每步 27.7–28.2 ms（原来 27.3–27.8 ms，这个版本的固定验证 28.3 ms），agent_bench 长回复每步 29.9 ms
  （原来 29.5–29.6 ms）。
- 多占约 1.2 GiB 显存（3、4 个请求的两档 CUDA 图和滑窗缓存 0.37 GiB，KV 池多的 512K token 0.86 GiB），decode 时每层少 1 个
  热专家槽，读长提示的显存峰值没有变高。
- 三个模型的回归通过；1–4 路照抄 0 错；4 个请求占满 512K 池、放不下时排队、把 1M 池占到 100 万 token，都正常。

## 多个请求同时的速度

同样的提示（各约 16K token 的不同源文件，各写 3,000 token，温度 0），取所有请求都在 decode 的那一段，每步 / 合计：

| 同时的请求 | 固定验证，一次 8 个 token（原来） | 固定验证，一次 16 个 | 变长验证，一次 8 个 | 变长验证，一次 16 个，补满档位（现在的默认） |
|---:|---:|---:|---:|---:|
| 1 | 27.3–27.8 ms / 129–140 tok/s | 28.3 ms / 146 tok/s | 28.3 ms / 136 tok/s | 27.7–28.2 ms / 121–139 tok/s |
| 2 | 45.3–46.6 ms / 173–177 tok/s | 42.4 ms / 192 tok/s | 37.0 ms / 188 tok/s | 38.1–39.0 ms / 191–197 tok/s |
| 4 | 80.8–82.0 ms / 198–201 tok/s | 75.9 ms / 212 tok/s | 54.8 ms / 230 tok/s | 48.8–49.8 ms / 251–254 tok/s |

固定验证每个请求每步都验 6 个 token，每步接受 3.6–4.3 个；变长验证按成本表少验一些（4 个请求时每步接受约 3.1 个），换来短得多的
一步。tok/s 随写出的内容变（接受长度不同），同一种验证之间比每步时间更准。采样聊天 4 路同时（6 题 × 2 轮）合计 193 tok/s
（固定验证、一次 8 个 token 时 157 tok/s）。

变长验证把留下的 token 排紧以后要补齐到捕获过的 CUDA 图的宽度（每个请求 6 行一档），补出来的行照样要算。启动脚本在变长验证时加了
SGLang 的 `--speculative-dspark-align-verify-tokens-to-graph-tier`：规划器选好档位以后，把这一档里补出来的行换成真的草稿 token。
不加的话，规划器按成本表会在一档里少验几个，而这一步的时间并没有少。同一版本，各两到四次：

| | 2 个请求同时 | 4 个请求同时 |
|---|---:|---:|
| 按这个版本量的成本表 | 37.2–37.4 ms / 186–190 tok/s | 48.8–50.5 ms / 237–245 tok/s |
| 按一次 8 个 token 时量的成本表 | 33.6–34.1 ms / 193 tok/s | 48.7–48.8 ms / 251–255 tok/s |
| 按这个版本量的成本表，补满档位（现在的默认） | 38.1–39.0 ms / 191–197 tok/s | 48.8–49.8 ms / 251–254 tok/s |

## 一个请求时

| | 上限 2、512K 池（11-11） | 上限 4、512K 池 | 现在：上限 4、1M 池、变长验证 |
|---|---:|---:|---:|
| 单请求每步（16K 提示，写 3,000 token） | 27.7 ms | 27.3–27.8 ms | 27.7–28.2 ms（固定验证 28.3 ms） |
| decode 时每层的弹性热专家槽 | +26–28 | +27 | +26 |
| 捕获 CUDA 图以后剩的显存 | 22.34 GiB | 21.97 GiB | 21.08 GiB |
| 520K 提示：显存峰值 | 70,586 MiB | 70,596 MiB | 71,152 MiB |
| 520K 提示：冷 prefill | 5,928–6,229 tok/s | 6,022 tok/s | 6,221 tok/s |

显卡可用 72,830 MiB。KV 每个 token 约 1.7 KB（FP8），多的 512K token 实测占 0.86 GiB；滑窗注意力的池（2.45 GiB）按分块大小和
请求数定，不随 KV 池变。显存由弹性热专家槽调剂：decode 时把空着的显存都拿去放热专家，要读提示时按预测的用量还回去，另留 2 GiB。
所以 KV 池加大以后少的是 decode 时的 1 个槽，读提示时的峰值仍由那 2 GiB 预留决定。各项测试里的最高峰值 71,688 MiB，
离可用上限 1.1 GiB。

## 一次专家调用最多 16 个 token

每个 MoE 层的专家按「调用」算：GPU 把这一步的 token 和路由交给 CPU，自己算热专家槽里的专家，CPU 算其余的。一次调用原来最多
8 个 token：两个请求的 12 行验证分成 8 + 4 两次，四个请求的 24 行分成三次，两个请求都路由到的专家在每次调用里各算一遍。现在一次
最多 16 个（引擎 `DECODE_M`、信箱 `MAX_SLOT_M`、`backend/method.py` 的 `slot_width`），12 行一次、24 行两次。同一份编译，
`XTIER_SLOT_TOKENS=8 / 16` 对照，固定验证：

| | 一次最多 8 个 | 一次最多 16 个 |
|---|---:|---:|
| 1 个请求每步 | 27.83 ms | 27.93 ms |
| 2 个请求同时：每步 / 合计 | 45.33 ms / 174 tok/s | 42.01 ms / 191 tok/s |
| 4 个请求同时：每步 / 合计 | 81.2 ms / 198 tok/s | 75.7 ms / 216 tok/s |
| 4 个请求时每层每步的专家调用 | 3 次，各 30.8 个专家、CPU 508 µs | 2 次，各 40.8 个专家、CPU 708 µs |

每步少约 7%：每层每步算的专家从 92 个降到 82 个。一个请求的调用不超过 8 个 token，不受影响。

- 一个槽最多放 128 条路由：top-8 以内 16 个 token，top-10（Qwen3.8）12 个。
- GLM-5.3、Qwen3.8 每个请求验 4 行，两个请求 8 行，原来就是一次调用；变的是不超过 64 个 token 的短提示（走同一条路径），
  调用次数少了。
- 第二张卡当热专家池时仍按 8 个（那条路径没有真卡重测）。尾部跳过（`XTIER_TAIL_SKIP`，默认关）只管不超过 8 个 token 的调用，
  两个请求合成的 12 个 token 不跳，要跳把 `XTIER_TAIL_SKIP_TOKENS` 设成 16。
- 单层测试覆盖到每个模型一次调用的上限（`mailbox_check` 逐位相同，`cache_check`、`miss_gpu_check` 在原来的误差内）；CPU 引擎的
  线程检查和内存检查 0 报告。

## 成本表：每步时间按 6 行一档

`tools/sps_profile.py`（现在默认测 1–4 个请求）在这个版本上量到的每步中位数：

| 请求数 | 一步验证的 token 总数 → 每步 |
|---:|---|
| 1 | 2 → 23.4 ms，3 → 25.0，4 → 26.9，5 → 28.2，6 → 27.4 |
| 2 | 4 → 28.2 ms，6 → 27.7，8 → 35.6，10 → 38.2，12 → 36.6 |
| 3 | 6 → 28.7 ms，9 → 36.2，12 → 43.4，15 → 50.6，18 → 60.1 |
| 4 | 8 → 37.0 ms，12 → 39.1，16 → 57.8，20 → 69.5，24 → 80.0 |

SGLang 的变长验证把留下的 token 排紧，再补齐到捕获过的 CUDA 图的宽度（6、12、18、24 行）。一步多少时间基本看落在哪一档，和
请求数关系不大（2 个请求各验 3 个 token 和 1 个请求验 6 个一样快）。4 个请求各验 3 个 token 是 39 ms，各验 6 个是 80 ms，所以请求多
的时候少验一点很划算，这是启动台默认改成变长验证的原因。一次调用 8 个 token 时 12 行那一档是 43–44 ms，现在 37–39 ms。
这张表是不带「补满档位」量的（它量的是每种 token 数的成本）。换机器要重测（[变长验证报告](2026-11-06-ds-compact-verify.md)里的
三步）；`run-ds-xtier.sh` 单独运行时默认仍是固定验证。

## FP8 投影的快内核：1–24 行

3、4 个请求的验证是 18、24 行，草稿是 15、20 行，原来的名单（1、4、5、6、10、12）里没有，会落回慢 3–4 倍的 CUTLASS 内核。
`tests/ds_mxfp8_rows_check.py` 把 1–32 行、5 种投影形状都对了一遍：两个内核的输出逐位相同，b12x 都更快（1280 → 32768 的投影
16–25 µs 对 92–162 µs，单测里权重在缓存中）。默认值改成范围 `1-24`，写法支持 `5,10-12`。

## KV 池 1M：子 agent 不再挤掉主会话的缓存

一个约 37 万 token 的会话读完以后，同时来 3 个各 8 万 token 的请求（子 agent），然后主会话带着新的问题回来：

| | 512K 池 | 1M 池 |
|---|---:|---:|
| 主会话第一次读（冷） | 367,437 token，首字 56.6 秒 | 382,429 token，首字 58.7 秒 |
| 3 个子 agent 的首字 | 15.0 / 33.2 / 42.5 秒 | 14.7 / 32.9 / 42.5 秒 |
| 主会话回来时命中的缓存 | 245,760 token | 382,208 token |
| 主会话回来的首字 | 19.9 秒 | 1.8 秒 |

512K 池放不下 37 万 + 24 万，SGLang 把最久没用的缓存（主会话的后 12 万 token）清掉了。启动台的 DeepSeek 卡片现在按 1M 的池起
（「上下文」一项的标题和说明里写着，没有做成选项）；`run-ds-xtier.sh` 读 `KV_POOL`，不设时和上下文一样。基线配置（加速包关）和
最小化配置的池不变，最小化配置也仍是 2 个请求。

## 修复：读完长提示以后热专家槽被误收回

弹性热专家槽每 16 个 decode forward 检查一次显卡的空闲显存，不足 1 GiB 就把额外的槽全部收回，10 分钟内不再加。它只看驱动报的空闲量，
而读完一段提示以后，PyTorch 的分配器把这次 forward 用过的显存留在自己的缓存里。KV 池加到 1M、并发放到 4 以后少了约 1.2 GiB 余量：
服务刚起来就读一个 128K 的提示，最后一块比预测多用 4 GiB，读完驱动报的空闲只剩 0.9 GiB（都在分配器的缓存里，随时可以再用），
检查就触发了。之后 10 分钟 decode 只有 35 个基础槽：单请求每步 30.9 ms（正常 28.2 ms），4 个请求同时 211 tok/s（正常 252 tok/s）。
前一天同样的测试（512K 池、2 个请求）刚好没到这条线，此前 84 份 DeepSeek 日志里没有出现过。

现在检查在低于 1 GiB 时先清空分配器的缓存再量一次，仍然不足才收回（加槽和 forward 之前的检查本来就是这样量的）。修复后同样的顺序
（刚起来先读两个 128K 提示）：没有再触发，热专家槽照常收放；随后单请求每步 27.7 ms，4 个请求同时 49.7 ms、254 tok/s。新测试 `tests/elastic_critical_check.py`（不需要显卡）。
