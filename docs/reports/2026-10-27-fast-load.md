# 2026-10-27：快速加载——专家直接从模型文件或冷存储读进引擎

问题：DeepSeek V4.1 Flash 1017 启动到报在线约 8 分钟（472 s），其中加载权重 367 s；312 GB 的检查点平均只读到约 0.9 GB/s，
它所在的 990 PRO 本身约 6 GB/s。参考 Strata / Project Maya 的加载方式，但不做它们那种“先上线、专家边用边读”：两种情况都在
报在线之前把专家全部装好、检查完。

## 原来慢在哪（py-spy 采加载线程 60 秒，DeepSeek，冷专家关）

| 在做什么 | 占比 | 每层约 |
|---|---:|---:|
| SGLang 把 w1 / w3 拷进 w13 参数（`_load_w13`，从检查点映射缺页读） | 28.8% | 2.3 s |
| XTier 把 [up; gate] 重排成 [gate; up]（`formats._gate_up` 的 `torch.cat`，整份 w13 再拷一遍） | 28.7% | 2.3 s |
| SGLang 拷 w2（`_load_w2`） | 13.8% | 1.1 s |
| 拷进引擎 NUMA 分片（`CpuPlan.__init__`） | 7.7% | 0.6 s |
| 其他转换、丢页缓存、wo_a 反量化 | 约 15% | 1.2 s |

同一份专家数据在内存里拷三遍，全在一个线程上；后台预读线程大部分时间闲着，盘不是瓶颈。

## 做法（`XTIER_FAST_LOAD=1`，默认关）

只改启动时把专家搬进 CPU 引擎的方式，模型、权重和推理都不变；默认（关）是 SGLang 原来的加载方式。

**不开冷专家：直接读模型文件**（`xtier/backend/direct.py`）

- 加载时 XTier 的权重钩子遇到专家的四个大参数（w13 / w2 的权重和块缩放），不调 SGLang 的拷贝，只记下这个张量在哪个文件、
  哪个偏移：SGLang 的张量是文件映射上的视图，按地址查 `/proc/self/maps`，并用 `/proc/self/map_files` 核对这段映射还是这个文件
  （上一个文件关掉后，下一个文件可能映射到同一段地址，第一版就因此读错过文件，单层测试抓到）。
- 一层到齐后，引擎建空槽：`xtier_create3 / create4` 的四个源指针全空时只分配、不拷贝（C++ 改动只有这一处）。16 个读线程用
  O_DIRECT 把张量读进 4 KiB 对齐的暂存区，再按 NUMA 节点分段拷进分片。同一文件里相邻的张量合并成最多 32 MB 一次读、按文件顺序，
  对无 DRAM 的盘（GLM、MiniMax 在 FX700 上）也是顺序读。
- 读盘在后台进行，加载线程接着处理下一层；整个模型加载完（`ModelRunner.load_model` 之后）统一等读完，并按引擎原来对源数据的
  规则检查块缩放（MXFP4 ≤ 254、E4M3 ≤ 126）。用到分片的步骤（NUMA 迁移、锁页、热专家池填充）都在这之后。
- 只在字节原样可用时走这条路：TP 1、单个专家的 w1 / w3 / w2、形状和引擎一致、一字节的数据类型；否则整层走原路径（如果一层里
  前面的张量已经记下、后面的对不上，直接报错，不混用两种行序）。
- 省掉的：主机参数那份拷贝、gate / up 重排、引擎拷贝；检查点不经过页缓存，加载后也不用再丢页缓存。

**开冷专家：从冷存储填槽**（`xtier/cache/cold.py`）

- 冷存储清单每层记下它对应的检查点（`source`：模型目录里 .safetensors 和 .json 的文件名、大小、修改时间）；原路径写入记录、
  或按权重核对记录通过时写上。写上之前先把记录刷到盘上（fdatasync），清单本身也 fsync 之后再替换：断电后不会出现“清单说
  对得上、数据还在盘的写缓存里”的层。
- 一层的记录布局和 `source` 都对得上时，整层跳过检查点里的专家张量（一个字节都不读），引擎建空槽，常驻槽从 4 块盘上的冷存储
  后台读进来（O_DIRECT，4 块盘并行；和直接读一样在加载结束时统一等完、检查块缩放），然后照原来的方式挂上冷专家。
- 第一次启动（或检查点变了）照原路径加载、写好或核对冷存储并记上 `source`，下一次启动起生效。
- 开冷专家时，冷专家层从冷存储填槽，其余的层（全部常驻的层、草稿模型的 MoE 层）直接读模型文件。

**核对**：`XTIER_LOAD_DIGEST=1` 在每层分片装好后记一条 SHA-1 摘要；`tests/direct_load_check.py` 对一层逐字节比较原路径和直接读
（四个模型），以及从源拷贝的常驻槽和从冷存储读出的常驻槽，并确认坏的块缩放会被拒绝。

## 结果

同一份代码 `XTIER_FAST_LOAD` 关 / 开各启动一次（原路径 / 快速加载），冷存储在 4 块 PCIe 4.0 盘上。报在线 = 从启动命令到
服务可用；加载权重 = SGLang 报的 load_weight（主模型 + 草稿模型）。

| 模型 / 情况 | 原路径：加载权重 / 报在线 | 快速加载：加载权重 / 报在线 | 报在线 |
|---|---:|---:|---:|
| DeepSeek V4.1 Flash 1017，不开冷专家 | 367 s / 472 s | 117 s / 186 s | −61% |
| DeepSeek，卸载 30% | 346 s / 409 s | 65 s / 124 s | −70% |
| DeepSeek 最小化卡片（32 GB + 128 GB，卸载 70%） | 339 s / 393 s | 62 s / 111 s | −72% |
| GLM-5.3 Flash | 301 s / 381 s | 146 s / 233 s | −39% |
| Qwen3.8 Flash Next | 242 s / 282 s | 220 s / 262 s | −7% |
| MiniMax-M3.1-Flash | 168 s / 228 s | 61 s / 126 s | −45% |

- 精度：两种路径每层分片的 SHA-1 摘要全部相同（DeepSeek 43/43、卸载 30% 43/43、GLM 43/43、Qwen 49/49、MiniMax 57/57），
  装进引擎的每个字节都和原路径一样。DeepSeek、GLM、Qwen 每次启动后照抄 0 错；MiniMax 见下。
- 端到端：DeepSeek 从 main 启动、开快速加载，各接一次 dsh 15 分钟（上下文填到约 20 万 token、召回、编码任务）。不开冷专家：
  185 s 报在线（43 层全部直接读），dsh 23 次 0 失败；卸载 30%：124 s（40 层从冷存储填槽、3 层直接读），dsh 11 次 0 失败。两次
  召回都 3/3、照抄 0 错、服务日志 0 错误。卸载 30% 那次最后 4 分钟冷专家读盘掉到每块盘约 47 MB/s（会话里每块盘已读约 1 TB），
  是 FX700 持续读塌速（见[冷专家设计](../design-cold-experts.md)），和加载方式无关，所以编码任务只跑了 7 个。
- MiniMax 的照抄：模型在思考里把全文逐行抄一遍、撞上 1,400 token 上限（照抄报 500 多错）的情况，原路径和快速加载都有（原路径
  4 次启动中 1 次，快速加载 4 次中 2 次）；MiniMax 跨启动本来就不确定，所有启动的输出都在前 85–203 个字符内分岔。逐 token 对比
  prefill logprob（原路径 / 快速加载 / 原路径各启动一次，每次两轮）：12K 文档三次逐 token 相同；两段 3K 每次启动都有一轮和
  第一次逐 token 相同，另一轮有时换成另一种结果，原路径两次之间也这样；600 token 那段每轮都不一样（走 CPU 和热专家池，池在变）。
  快速加载没有带来原路径之外的差别；main（13a4cc7）本身启动一次，和关着开关的原路径逐 token 相同（600 token 那段除外，它在
  main 自己的两轮之间也差 16.9）。
- 带摘要的那组启动（每层算一次摘要，多花一些时间）是第二个样本：DeepSeek 457 → 201 s，卸载 30% 424 → 149 s（第一版：同步填槽、
  草稿那层走原路径），GLM 402 → 249 s，Qwen 286 → 272 s，MiniMax 289 → 177 s；MiniMax 快速加载不带摘要的第二次 136 s。
- 冷存储填槽只在 DeepSeek（MXFP4）上实测：GLM / Qwen / MiniMax 的测试冷存储在 10-27 凌晨的回归之后删了。代码与格式无关
  （六段的排法和冷专家读写相同，全局缩放照旧从检查点来），给这三个模型用之前先写一次冷存储、带 `XTIER_LOAD_DIGEST=1` 对一次摘要。
- 读盘在后台，但没有拖到加载之后：主模型加载完到草稿模型开始加载只隔约 2 s，两种路径一样。
- 所需内存不变：内存最低点在加载之后（分片锁页、KV 等），两种路径相同；最小化卡片加载期间不可回收内存的峰值 99.4 / 99.2 GiB。
- Qwen 只快 7%：专家只占检查点的一半（68 / 129 GB），每层又小（1.4 GB）；时间在主模型的其余部分（208 个文件，约 0.7 GB/s，
  还没剖析）和 MTP 草稿模型（44 s，见下）。

## 剩下的时间

DeepSeek 不开冷专家，各阶段（秒，从日志的 server_args 那行算起，之前还有约 13 s 进程启动）：

| 阶段 | 原路径 | 快速加载 |
|---|---:|---:|
| 初始化（CUDA、分布式） | 14 | 15 |
| 主模型权重 | 356.6 | 113.9 |
| 草稿模型（DSpark） | 10.7 | 3.2 |
| NUMA 迁移 | 36.3 | 2.6 |
| 锁页（GPU prefill 从分片上传要用） | 22.6 | 20.1 |
| 其余（热专家池、CUDA 图、起服务） | 17.1 | 15.3 |
| 合计 | 459 | 173 |

- NUMA 迁移 36 → 2.6 s：分片的页按“优先本节点”分配，原路径的检查点经过页缓存，有的节点被页缓存占满时分片页落到别的节点，
  加载后要迁回来；快速加载不经页缓存，页一开始就在对的节点上（卸载 30% 时内存宽松，原路径也只要 6.9 s）。
- 主模型 114 s 读 310 GB 专家，约 2.7 GB/s，是 990 PRO 顺序读的 45%。读线程 81% 的时间在把暂存区拷进分片（新分片第一次写入
  要缺页、清零），平均只有约 4.5 个线程在忙；加载线程只有约 34% 的时间在跑，其中 DeepSeek wo_a 的 FP8 反量化 33%、等 SGLang
  的下一个文件 21%、丢页缓存 17%。
- 卸载 30%（快速加载，从 server_args 起 112 s）：主模型 61.8 s、草稿 3.2 s、NUMA 迁移 1.9 s、锁页 14.1 s、其余 15 s。
  常驻槽约 200 GB 从冷存储读（4 块盘 15–18 GB/s，十几秒，后台），主模型的时间主要是 SGLang 逐个过 48 个文件：加载线程约 69%
  的时间在跑，其中约 1/3 是 wo_a 的 FP8 反量化（SGLang 加载时在 CPU 上反量化成 BF16，加速包再逐位核对后转回 FP8）、17% 丢页缓存。
- 可以接着做的（都没做）：
  - 分片的页由各节点的线程预先分配好（或用大页），读线程直接拷进已有的页：估计不开冷专家时主模型 114 → 60–80 s。
  - wo_a 不在 CPU 上反量化（直接留 FP8，或放到 GPU 上做）：开冷专家时估计 −10–15 s。
  - 锁页和加载重叠：快速加载时页本来就在对的节点上，每层读完就锁，DeepSeek 约 −15–20 s。
  - 草稿模型只打开含草稿权重的文件：Qwen 的 MTP 草稿和主模型在同一个目录，现在 208 个文件都过一遍（44 s）；GLM 的 NextN 26 s。
  - Qwen 主模型的其余部分剖析一次。
