# 2026-10-30（下午）：跟进 SGLang main 6162b07

XTier 跟着官方 SGLang main 走。这次从 10-22 的 `8cd3c494` 跟进到 10-30 的 `6162b07199`（上游 592 个提交）。起因是
[#2](https://github.com/a775828b-dot/xtier/issues/2)：在新版 main 上，DeepSeek V4.1 的 Engram 行放 NVMe 时启动就崩，
prompt 编码的钩子也挂不上。同时处理了另外三个 issue：
- [#3](https://github.com/a775828b-dot/xtier/issues/3)：快速加载在 TP > 1 时悄悄退回普通加载。
- [#4](https://github.com/a775828b-dot/xtier/issues/4)：英伟达官方 GLM NVFP4 检查点开 MTP 时崩溃。
- [#5](https://github.com/a775828b-dot/xtier/issues/5)：启动台在 chroot 里误选 systemd。

## 版本

- **测试过的提交**：写在安装步骤里（`git checkout 6162b07199`），也记在 `xtier/__init__.py` 的 `SGLANG_COMMIT`。插件装钩子前
  会核对已装 SGLang 版本号里的 `+g<提交>`，不一致就在日志里警告。
- **`tools/check_sglang.py`**：不用模型，核对三件事：SGLang 的提交；XTier 注册的全部钩子目标（所有加速包、所有功能打开时共 66 个）；
  从 sglang 的 import（44 处）。SGLang 的 HookRegistry 遇到挂不上的钩子只记一条日志就接着跑，这个脚本在起服务前把它们全部列出来。
- **新版 SGLang 的依赖**：
  - 新增：deepseek-recipe 0.2.0、sgl-flash-mla 1.0.0、tml-renderers 0.1.0、python-dateutil < 3。
  - 升级：sgl-deep-gemm 0.2.3 → 0.2.3.post2、timm 1.0.16 → 1.0.25。
  - 不变：torch、flashinfer、sglang-kernel。
- **Rust 工具链**：SGLang 的安装脚本现在要用它发现可选的 Rust 扩展（gRPC、前缀树、V4.1 图片预处理）。没装 Rust 就加
  `SGLANG_BUILD_RUST_EXTS=none`，缺扩展时上游自动退回 Python 实现（旧版本来就是 Python 实现）。

## 升级改了什么

XTier 在所有功能打开时注册 54 个钩子。逐个比对被钩函数在两个提交间的源码：36 个没变，1 个目标没了，15 个有改动；另有 2 个是
tilelang / flashinfer 的，这两个包的版本没变。要改的有 4 处：

- **DeepSeek V4.1 Engram 行放 NVMe**（`XTIER_ENGRAM_ROWS=nvme`）：
  - XTier 替换的 `EngramEmbedding.__init__` 补上了上游 10-23 以后新增的属性：跨卡读取 `peer`、调度进程暂存
    `staged_by_scheduler`、主机表 `_sort_host_reads`、DP 查表方式 `lookup` 和 `_cols_per_rank`。
  - 这些路径都不管 NVMe 上的行，`forward` 照旧走 `_lookup` → XTier 的 `_owned_rows`。
  - 解析出的查表方式如果是 peer_read（NVMe 上做不到），就退回 all_reduce。
- **DeepSeek V4.1 的 prompt 编码**：上游从 `e22a530`（10-23）起直接用 DeepSeek 官方的 deepseek-recipe 把 V4 / V4.1 对话编码成
  token id。XTier 的 `recipe_tokens` 做的就是同一件事（按 deepseek-recipe 的规则分词），所以删掉了。
- **MoE 方法**：上游的 KT 包装在 `apply` 里把"跳过式"的 top-k 输出转成标准格式，顶替它的 `XTierMoEMethod` 也照做。
- **Qwen PLE 分段 prefill**：KV 池改成按层路由（`layer_router`），短卷积状态改从池的新接口取。

其余 12 处要么是包一层再调用原函数，要么上游只加了参数或改了注释，不用改：
- wo_a、DSpark lm_head 投影、索引器。
- 投机解码的 3 个钩子。
- Engram 哈希与层初始化；`_owned_rows` 是 XTier 整个替换的，上游改的只是它自己那份实现。
- `ModelRunner.forward`、QSA 的两个。

## 回归

测试条件：
- **硬件**：单卡 RTX PRO 5000，功耗墙 300 W。
- **参数**：启动台默认参数（512K 上下文、加速包、投机解码）。Qwen 和 DeepSeek 用快速加载；GLM 用普通加载（它所在的那块无 DRAM
  缓存的硬盘当天多路并发读时掉速，与本次改动无关）。
- **对比口径**：和 10-23 旧版 SGLang 的同口径结果比，旧数是在 350 W 下测的。
- **测法**：照抄、PPL、长上下文分别用 `bench/copy_test.py`、`bench/ppl_eval.py`（13 段 × 4K）、`bench/context_speed.py`。
- **dsh**：编码代理连续跑 15 分钟（先读 20 个笔记文件约 10 万 token，回忆后接简单编码任务）。

| 项目 | Qwen3.8 Flash Next | GLM-5.3 Flash | DeepSeek V4.1 Flash 1017 |
|---|---|---|---|
| 照抄（单路 / 两路） | 0/8、0/8 | 0/8、1/8，重跑 0/8 | 0/8、0/8 |
| PPL（新 / 旧） | 3.4812 / 3.4808 | 3.9974 / 3.9982 | 3.3183 / 3.3187 |
| 64K 冷 prefill 首字（新 / 旧） | 12.2 / 11.9 s | 25.3 / 23.4 s | 13.6 / 15.7 s |
| 64K decode 每步（新 / 旧） | 14.5 / 14.4 ms | 28.9 / 29.2 ms | 29.6 / 32.6 ms |
| 52 万 token（满上下文） | 不 OOM，首字 108 s | 不 OOM，首字 208 s | 不 OOM，首字 112 s |
| dsh 15 分钟 | 69 轮 0 失败，回忆 3/3 | 35 轮 0 失败，回忆 3/3 | 21 轮 0 失败，回忆 3/3 |

- **64K 的首次测量**：换版本后第一次测 64K 时，首字慢很多（Qwen 18.5 s），因为新版 SGLang 的 JIT 内核要重新编译。表里是缓存热了以后的数。
- **DeepSeek 两路照抄**：有一次结尾多出 `</src>`，正文逐字一致，这是旧版基准里就记过的现象。
- **GLM 两路照抄**：有一段把 `DetachHiCacheStorageReqInput` 抄成了 `DetachHiCacheReqInput`，重跑一遍 8 段全对。这一段（第 2 段，
  一长串格式相同的注册行）在 FP8 权重下偶尔会错一个 token（漏一个词，或少 4 个缩进）。10-23 旧版 SGLang 开 FP8 权重时，同一段
  同一位置也错过一次，关掉 FP8 权重则是 0 错。这是 FP8 权重的数值问题，不是这次升级带进来的。
- **GLM 64K prefill**：比 10-23 的旧数慢约 8%。那组数是在 60 槽、不开弹性、350 W 下测的，配置不完全相同；和 10-26 按启动台默认
  配置测的冷 prefill（2,682 tok/s）比，这次 2,589 tok/s，差 3.5%。

## 快速加载支持张量并行（#3）

MoE 张量并行时，SGLang 的加载器给每个 rank 专家中间维的一段：w1 / w3 的行、w2 的列，连同它们的块缩放。改动如下：
- **w1 / w3**：rank 要的行在文件里是连续的一段，只读这一段。
- **w2**：rank 要的列分散在每一行里，所以整块读进来，再用一次 numpy 跨步拷贝取出自己那几列。
- **读取量**：每个 rank 读的字节约是整层的 2/3（w2 多读一倍）。
- **之后的流程**：rank 自己那份照旧按 NUMA 节点切开放进引擎。
- **退回提示**：还读不了的层退回普通加载时，会记一条警告（每个进程一次）。

验证（`TP=2 tests/direct_load_check.py`，单卡机器上模拟每个 rank）：
- **测法**：直接读取填出的分片，和"该 rank 拿到的那一段"经引擎拷贝出的分片逐字节比对。
- **结果**：DeepSeek V4.1 1017（MXFP4）、GLM-5.3（NVFP4）、Qwen3.8（NVFP4）的两个 rank 都逐字节相同。TP=1 的原有对比也全部通过。
- **双卡实测**（2026-10-31，双 RTX 4090，`--tp-size 2`，`XTIER_LOAD_DIGEST=1`）：Qwen3.8 整模型权重加载 170.2 → 132.5 s，96 个
  分片的摘要与普通加载全部相同，照抄单路、两路都是 0/8；GLM-5.3 截 8 层 42.4 → 14.9 s，10 个分片全部相同。DeepSeek V4.1 1017
  （MXFP4）还没在两张卡上跑过，只做了上面的逐字节对比。

## 官方 GLM NVFP4 检查点开 MTP（#4）

英伟达官方 ModelOpt 检查点（nv-community/GLM-5.3-Flash-NVFP4）把 NextN 层（第 45 层）排除在量化之外，是 BF16。XTier 测试用的
LibertAIDAI 版，这一层的专家是 NVFP4。XTier 的 GLM 钩子原来默认 NextN 是 NVFP4，遇到官方版就会崩。现在：

- **钩子先看排除名单**：用 `quant_config.is_layer_excluded('model.layers.45.mlp.experts')` 判断，NextN 被排除时不再遮蔽
  `get_name`，SGLang 照常把 NextN 当 BF16 建。
- **KT 包装的兜底**：回退路径拿到空的量化方法时，先换成 `UnquantizedFusedMoEMethod`，和 SGLang 不走 KT 时的做法一样。
- **小显存**：BF16 的 NextN 专家共 288 个、约 13.5 GiB，留在显卡上的话 32 GB 的卡放不下。现在 `XTIER_DRAFT=1` 时，草稿层的 BF16
  专家在交给 CPU 引擎前量化成 NVFP4，格式和 ModelOpt 相同：全局缩放取 amax / (6 × 448)，每 16 个值一个 E4M3 块缩放，E2M1
  四舍五入到最近值；之后和主模型的 NVFP4 层一样运行。
- **精度影响**：这只改变草稿模型的精度，也就是影响接受率，不影响输出正确性，因为草稿提出的每个 token 都要主模型校验。主模型的
  BF16 专家不会这样转。

验证：

- **测法**：没有下载官方检查点，而是把 LibertAIDAI 版第 45 层的 864 个 NVFP4 专家权重解量化成 BF16、去掉它们的缩放，再把第 45
  层加进排除名单，造出和官方版一样的情况。测完已删除。
- **结果**：开 EAGLE（`XTIER_DRAFT=1`）能正常启动。加载时 288 个草稿专家用 10.1 s 转成 NVFP4，交给 CPU 引擎；显存占用和原检查点
  相同。64K 时接受长度 2.79 / 2.82，原检查点（草稿本来就是 NVFP4）是 2.76–2.85。照抄单路有一处错，就是上面说的第 2 段 FP8 权重的
  偶发翻转。温度 0 时每个 token 都由主模型决定，这处错和草稿无关。
- **单元测试**（`tests/draft_bf16_check.py`）：随机矩阵量化后的误差都在一个块缩放以内；把一层真实的 NVFP4 专家解成 BF16，再用这个
  格式重新量化，得到的值和原来完全一样（相对 RMS 为 0）。

## 启动台的 runner（#5）

- **原来的判断**：`runner=auto` 原来看 `systemctl --user show-environment` 的退出码。但在 chroot 里它会忽略命令、照样返回 0，
  于是选了 systemd，启动模型时 `systemd-run --user` 连不上总线就失败了。
- **现在的判断**：实际试跑一次 `systemd-run --user --scope --quiet --collect true`，能起 scope 才选 systemd，否则退回 setsid。
  显式指定 `--runner systemd` 时行为不变。
- **测试**：`tests/console_check.py` 加了模拟的检查：systemctl 返回 0、systemd-run 连不上总线 → setsid。
