# XTier 工作计划

## 目标

在官方 SGLang（跟 main 分支）上，用一个插件包实现 CPU/GPU 分层 MoE 推理：专家分布在显存和内存两层，按热度放置、按需调度；NVMe 只放大嵌入表的行（DeepSeek 的 Engram、Qwen 的 PLE）。
三个模型（DeepSeek V4.1 Flash 1017、Qwen3.8 Flash Next、GLM-5.3 Flash）的速度和精度对齐现在的生产管线后切换过去；以后加新的 MoE 模型不需要写混合推理代码。

## 原则

- **不改 SGLang 源码**：只用官方插件框架（`sglang.srt.plugins` 的钩子）。官方改名或删掉了钩子目标，启动时直接报错。
- **与模型无关的核心**：混合推理包在官方 `FusedMoE` 的量化方法外面，任何用标准 MoE 层的模型装上就能跑。
- **加速包可选**：某个模型独有的优化放在 `xtier/packs/<官方模型模块名>/`，不装也能正确运行；能通用的优先提交给官方。
- **生产不动**：开发用独立环境、独立端口；每个模型达标才切换，旧管线保留到稳定为止。
- **用数据验收**：每一步都有门槛，基线就是现在三条生产管线的实测。
- **自己确认生效**：SGLang 会吞掉插件里的异常，XTier 加载模型时检查后端确实接管了 MoE，没接管就报错退出，不允许悄悄退回纯 GPU。

## 架构

```
SGLang 官方 main（固定到验收通过的提交号，每周同步）
└─ xtier（本仓库，一个包、一个版本号）
   ├─ backend/   混合 MoE 后端：包装官方量化方法；权重分流、decode 调度、prefill GPU 路径、CUDA 图兼容
   ├─ cache/     全局专家缓存：所有层共用显存预算，按热度和收益放置、在线换入换出；一个 GPU 专家内核
   ├─ planner/   自动规划器：探测显存、PCIe、CPU 内存带宽和 NUMA，结合路由统计算出缓存、分块、线程，目标 CPU 和 GPU 同时算完
   ├─ engine/ + csrc/   CPU 引擎：AVX-512 / AVX2 专家内核、NUMA 线程池、CPU 与 GPU 之间的信箱通信、预取
   ├─ packs/     加速包：deepseek_v4、qwen4_exp、glm5_next、minimax_m3、speculative
   └─ console/   启动台：选模型、调参数、启停、加载阶段与遥测；计划加「自动规划」按钮和模型的添加 / 删除（第 8、9 步）
```

## 阶段

### 0. 盘点与基线（2–3 天）

- 0.1 改动清单：把三条生产管线和 CPU 引擎相对官方 SGLang 的每一处改动按**功能**列出来，每项标落点：
  XTier 后端 / 加速包 / 官方已有（删）/ 临时绕法（删）。产出 `docs/inventory.md`。
- 0.2 基线固化：三条管线现在的验收数据整理成机器可读的基线文件和测法脚本（`bench/baselines/`）。
- 0.3 官方 main 摸底：新环境装官方 main，确认三个模型各自的 MoE 调用路径、量化方法、投机解码方式；Qwen 专用 decode 路径
  （`qwen4_decode_moe`）的接法。

### 1. 骨架与 CPU 引擎迁移（约 1 周）

- 构建（pyproject + C++ 编译）、插件入口、声明式配置格式（取代现在分散的环境变量）。
- CPU 引擎源码迁入 `csrc/` 并公开；去掉旧的兼容接口和环境变量。
- 门槛：单层输出与旧引擎 0.5.6 **逐位一致**，单层耗时不慢（三个模型的实权重单层对照）。

### 2. 混合 MoE 后端 + 全局专家缓存，先做 Qwen（约 2 周）

- 包装 `FusedMoE` 量化方法：CPU 专家权重直接进 NUMA 内存，缓存的专家进显存；decode 时命中缓存的走 GPU，其余走 CPU 信箱；
  prefill 走 GPU 上传流水；CUDA 图可捕获。
- 全局专家缓存取代"整层常驻 + 每层热专家池"；GPU 专家内核先做微基准，对齐 Marlin 和现在热专家池内核（0.94–0.95 TB/s）。
- qwen4_exp 加速包：hc_mix 重叠内核等（以盘点结果为准）。
- 门槛（对比现生产）：每个验证步不慢于 13.75 ms 的 2%；2 并发合计不低于 202 tok/s 的 98%；PPL 3.48 在噪声内；
  照抄测试单请求 / 两请求 0 错；512K 召回正确。

### 3. 自动规划器（约 1 周，可与第 4 步并行）

- 硬件探测 + 路由统计 → 缓存大小、分块、线程、并发下的显存预算，按"CPU 和 GPU 同时算完"分配。
- 门槛：三个模型自动配置的结果不差于现在手工调出来的生产配置。
- 2026-10-24 第一版（[planner.md](planner.md)、[报告](reports/2026-10-24-planner.md)）：热专家槽数已能自动定，Qwen 的方案按 agent_bench
  冷 prefill +2.4–2.9%、decode 持平；GLM / DeepSeek / MiniMax 均匀分槽已近最优。遗留：
  - 3.1 显存预算自动化：测启动后图后余量和最长 prefill 的显存峰值，余量加进热专家预算；建 prefill 分块 / 预取深度的显存与速度模型，
    在"多放热专家"和"大分块 / 深预取"之间取舍（GLM、MiniMax 现在显存已满，只能这样换）。
  - 3.2 探测贴近真实服务：调用之间插 GPU 工作、轮换多层（现在单层背靠背调用比服务里每次信箱调用少约 28 µs，靠 `call_us` 标定）；
    `XTier cache:` 统计改成按层，直接求每层的自适应系数。
  - 3.3 CPU 线程数（在独立进程里按几个线程数探测）、换入节奏（4 / 16 对 2 / 32，GLM 实测后者每步 −0.7%）纳入规划。

### 4. GLM 加速包（约 1 周）

- glm5_next：EAGLE 自适应步数、无损拒绝采样、截断验证、NoPE 稀疏 MLA（sm_120）等（以盘点结果为准）。
- 门槛：8 点测速平均不低于 106.9 tok/s 的 98%；2 并发合计不低于 112.4 tok/s 的 98%；PPL 4.06 在噪声内；照抄 0 错；512K 召回。

### 5. DeepSeek 加速包（约 2 周）

- deepseek_v4：Engram NVMe（支持多卡）、DSpark 固定验证、MXFP4 适配、FP4 索引器、官方编码等（以盘点结果为准）。
- 门槛：agent_bench decode 不低于 144–157 tok/s 的 98%；冷 prefill 不慢（64K 3.4K、128K 4.2K tok/s，522K 首字 142.7 s）；
  PPL 在噪声内；照抄 0 错；512K 召回；2 并发正常。

### 6. 切换生产（每个模型达标即切）

- WebUI 加新档位，和旧管线并行一段时间；旧管线保留回滚，稳定后归档。
- 原来三个公开仓库（lsglang_ds4.1 / lsglang_glm5.3 / lsglang_q3.8fn）改为部署配方：启动配置、测速结果和报告。

### 7. 持续：每周跟 main

- 拉官方 main → 单元测试 + 三个模型的快速验收（PPL、照抄、短测速）→ 通过才更新受支持的提交号，写进版本说明。

### 8. 启动台：「自动规划」按钮（约 3 天，依赖第 3 步）

目标：启动台模型栏里每个模型下面加一个「自动规划」按钮，点一下就在本机跑规划器，给出这个模型的推荐配置，可以一键设为默认或
按推荐启动，不用再手动跑 `plan_probe` / `plan_trace` / `plan_auto`。

- 8.1 规划服务（`xtier/planner/service.py`，与界面无关；命令行 `tools/plan_model.py 模型` 也能跑）：一个入口串起
  探测 → 档案 → 校准 → 方案，输出一份推荐（布局 = 全常驻层 + 每层槽数，写成 `XTIER_CACHE_PLAN` 文件；模型预测的 decode 每步和
  prefill 上传、与当前默认的差；依据 = 探测日期、档案窗口数、自适应系数；保护规则是否保留了手工布局）。
  - 探测按"本机指纹（GPU 型号与数量、CPU 型号、NUMA 节点、引擎指令集）× 层形状 × 线程数"缓存在 `~/.cache/xtier/`，指纹变了或
    超过 30 天才重测。探测要独占 GPU 和专家线程：有模型在跑时先问是否停掉；探测已缓存时规划本身不碰 GPU（约 1 秒）。
  - 档案：用模型条目给的带 counts 的档案，或启动台上次采集的；都没有时推荐里给「采集档案」：按当前配置起服务、开
    `XTIER_ROUTE_TRACE`、跑内置负载（短提示 + 64K，约 15 分钟）→ `plan_trace` 生成档案。
  - 校准：有该模型最近一次运行的日志就用 `plan_calibrate` 求自适应系数，否则用条目里的值；`call_us` 跟本机探测存在一起。
- 8.2 模型条目声明规划所需的信息：`configs/*/console.py` 的 `MODEL['planner']`（层形状预设或检查点路径、验证宽度、档案、手工布局、
  自适应系数）；布局选项加「自动规划」一个取值，`build()` 收到它时用状态目录里该模型的方案文件（`XTIER_CACHE_PLAN=<文件>`）。
- 8.3 启动台：`Jobs` 加规划任务（与启动任务互斥，一次一个）；接口 `POST /api/plan`（开始）、`GET /api/plan?model=`（最新推荐）、
  `POST /api/plan/apply`（设为默认：保存的参数里布局改成「自动规划」）。页面：按钮 → 进度（探测本机 → 读取档案 → 计算方案）→
  结果面板：当前 vs 推荐（全常驻层数、每层槽数范围、热专家显存、预测 decode 每步和 prefill 上传），分清"模型预测"和"已实测"，
  按钮「设为默认」「按推荐启动」「采集档案」。WebUI 里的启动台（私有适配层）接同样三个接口。
- 8.4 以后扩到其他旋钮：显存预算（3.1）、换入节奏、线程数（3.3）、prefill 分块，推荐里逐项列出。
- 门槛：Qwen 点按钮得到的推荐与 10-24 晚 agent 实测的方案一致（29 层全常驻 + 18 × 64–88 槽），「按推荐启动」后复测在噪声内；
  GLM、DeepSeek、MiniMax 的推荐保留手工布局并写明原因（均匀分槽已近最优 / 显存已满）；有模型在跑且探测已缓存时规划不碰 GPU；
  `tests/console_check.py` 覆盖规划接口（用假规划器，不起模型）。

### 9. 启动台：添加 / 删除模型（约 4–5 天）

目标：新增模型不再写 `configs/<目录>/console.py`，在启动台里填表添加、确认后删除；配合第 8 步自动生成默认配置。

- 9.1 声明式模型条目：一份 JSON（id、名称、服务名、端口；模型 / 分词器路径、Python 环境；SGLang 参数：上下文、KV 精度、分块、
  投机解码（无 / EAGLE / NEXTN / DSPARK 及草稿参数）、推理与工具调用解析器、显存比例；XTier：线程、热专家槽或「自动规划」、档案；
  卡片文字），存在启动台状态目录的 `models/` 下（不进仓库）。通用构建器 `xtier/console/generic.py` 把它变成（环境变量，命令行），
  启动 / 停止 / 遥测走现有逻辑。仓库里的 `configs/*/console.py` 作为内置条目保留，以后可以逐个改成 JSON。
- 9.2 添加：表单里选模型目录（限定在配置的模型根目录下）→「检测」读 `config.json` 和量化配置：模型类型、层数、专家数、top-k、
  隐藏 / 中间维度、专家格式（NVFP4 / MXFP4），匹配 SGLang 的模型类、XTier 加速包和解析器，给出默认值（上下文按显存粗估；带 MTP /
  草稿时开投机解码）→ 用户修改 → 校验（路径可读、端口没被其他条目或进程占用、服务名唯一、环境存在、权重 + KV 粗估放得下）→
  保存，模型栏出现卡片。可选「试启动」：起到就绪后自动停，记下加载时间和图后显存余量（第 8 步的显存预算用）。
- 9.3 删除：只能删用户添加的条目（确认框；运行中的不能删）；条目连同它的方案和档案移到状态目录的回收区，可恢复。内置条目只能在
  启动台里隐藏。
- 9.4 编辑：同一张表单改已有的用户条目，先校验，正在运行的下次启动生效。
- 9.5 安全：启动台按条目执行命令，所以只收白名单字段和取值，路径限定在模型根目录，不拼自由文本的 shell；额外的 SGLang 参数只能从
  白名单里选。启动台只听 127.0.0.1（WebUI 那边有登录）。
- 9.6 WebUI：8000 入口只认生产端口（代理辅助脚本），新模型要么从端口池分配、要么扩展私有适配层的 `PORTS`（不开源部分，单独做）。
- 9.7 与第 8 步衔接：新模型没有手工布局 → 首次规划先不开热专家起一次（测图后余量、最长 prefill 的峰值 → 显存预算，即 3.1），再
  探测 + 采集档案 + 规划，结果设为默认。这样"添加 → 自动规划 → 启动"全程不写代码。
- 门槛：用表单按 GLM-5.3 的参数添加一个条目，生成的环境变量和命令行与内置 `configs/glm53-pro5000-nps4` 的 `build()` 逐项相同
  （`console_check` 比对），起服务后照抄和对话检查通过；再加一个仓库里没有的 MoE 模型，走 检测 → 自动规划 → 启动 能正常服务；
  删除后卡片消失、回收区可恢复、运行中的条目删不掉。

## 风险与对策

| 风险 | 对策 |
|---|---|
| 官方 main 变化快，钩子目标会变 | 固定提交号，每周验收后再升级；钩子挂不上时启动即报错 |
| 现生产有不少深入 SGLang 核心的优化 | 盘点逐项判断；官方已有的删掉；必须保留的做成整函数替换钩子，并尽量提交给官方 |
| 全局缓存的 GPU 内核达不到 Marlin | 第 2 步先做内核微基准，达不到就保留整层路径作为缓存的特例 |
| 插件异常被 SGLang 吞掉 | 加载模型时自检，后端未接管即报错 |
| 测试要用 GPU | 测试窗口停 DS 生产服务，按现在的做法 |
