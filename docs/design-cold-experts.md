# 设计：冷专家池放到硬盘（`xtier/cache/cold.py`、`csrc/cold`）

内存放不下一个模型的全部路由专家时（例如 DeepSeek V4.1 Pro 在 72 GB 显存 + 384 GB 内存的机器上），每层只在内存里放一部分专家，
其余放在 NVMe 上的冷专家池里，用到时读进内存再算。池子大小和速度受限于硬盘的速度和类型：decode 每步要读它没命中的专家，
prefill 每次调用要把这一层用到的冷专家读一遍。`XTIER_COLD=1` 打开，默认关。实测见
[报告](reports/2026-10-26-cold-experts.md)。

开发用 DeepSeek V4.1 Flash 1017（40 层 × 384 个专家，每个专家 MXFP4 18.8 MB，全部 289 GB）限制内存模拟：每层只给
(1 − X) × 384 个内存槽。

## 结构

- **冷存储**（`csrc/cold/store.cpp`，编进 `libxtier_engine.so`）：每块盘一个文件，读写都用 O_DIRECT（不经页缓存：测到的就是盘，
  也不额外占内存）。一条记录 = 一个专家在 8 个 NUMA 节点上的分片，每片 2.35 MB（gate、up、两段 scale、down、scale 六段，
  就是引擎内存槽里的排法）；一条记录的 8 片分到各盘（`XTIER_COLD_PARTS` 可按盘速度给快盘多分，默认平均），读一个专家时
  所有盘同时出力。每块盘 8 个读线程；forward 等着的同步读排在 prefill 的异步读前面。清单（第一个目录的 `KEY.json`）记每层
  每块盘的起点和分法，重启时复用：每条记录核对首尾 4 KiB 的 CRC，不对或分法变了就整层重写。
- **分段**（`XTIER_COLD_UNITS=3`，默认 1）：盘数和 8 对不上、或者盘速不一样时，整片分太粗（6 块盘最好也只能 2:2:1:1:1:1，
  快盘和慢盘读得一样多）。分 3 段时每片切成 gate、up、其余四段三部分（差不多一样大；gate 和 up 各按 512 字节对齐切成四块读），
  一条记录 24 段，由 `XTIER_COLD_PARTS` 按盘速分，例如 4 块 PCIe 5.0 加 2 块 PCIe 4.0 用 `5:5:5:5:2:2`（大段先给按份额最空的盘）。
  存储名多一个 `-u3`，清单记下段数和每段在哪块盘（`units`、`map`）；没有这两项的旧清单按整片读，所以默认设置照常复用旧存储。
  已有的存储用 `tools/cold_relayout.py` 换布局（换盘、换段数、换分法）：逐条读出、写进新布局、读回逐字节比对，全部对上才写新清单，
  旧存储不动。模型打过洞时，这是改布局的唯一办法。同样快的 4 块盘不用分段：段小（DS 每段约 0.8 MB）、读请求多 3 倍。
- **内存槽**（`csrc/engine`，`xtier_create4`）：NUMA 分片只给 C = (1 − X) × 384 个槽，`slot_of` / `expert_of` 两张表。
  冷库存全部专家，任何专家都能换出，同一份存储可用于任意 X（常驻核心测过、没有采用，代码已移除，见「否决」）。
- **启动时从冷存储填槽**（快速加载 `XTIER_FAST_LOAD=1` 的一部分，默认关）：清单每层记下记录对应的检查点（`source`：
  模型目录里 .safetensors / .json 的文件名、大小、修改时间），记录刷到盘上（fdatasync）之后才写进清单。再次启动时布局和
  `source` 都对得上的层跳过检查点里的专家张量，引擎只分配槽，常驻槽从冷存储后台读入；加载结束时统一等完、检查块缩放，之后
  才做 NUMA 迁移、锁页和热专家池。对不上的层照原路径加载并写好 / 核对记录。DeepSeek 卸载 30% 报在线 409 → 124 s
  （[报告](reports/2026-10-27-fast-load.md)）。
- **换入换出**：forward 开始前，把这次路由到但不在内存的专家读进“衰减使用次数最低”的槽（半衰期 50 次调用，
  `XTIER_COLD_HALF_LIFE`；不选这次调用要用的、正被 GPU 复制锁定的）。计数只记 CPU 的使用，所以 GPU 热专家池里的专家
  （decode 时由 GPU 算）会先离开内存，把槽让给 CPU 要算的专家；它们启动时的计数为 0（其余按排名给初值）。
  `XTIER_COLD_OVERLAP=1`（默认）：先发读、算已经在内存里的专家，读完再算缺的那几个，两段结果相加（不再与一次算完逐位一致，
  差在 FP32 末位）。
- **GPU 热专家池**：只从内存槽上传；换入时先锁定内存槽（`xtier_slot_pin`），复制落地后解锁；不在内存的专家这一轮不换入。
- **GPU prefill**（≥ 1024 token）：每次调用按当时的槽表建一个虚拟专家顺序——内存槽在前、冷专家在后，路由 id 在 GPU 上映射，
  全局 scale 和 FP4 驻留表跟着重排。冷专家读进锁页暂存区（排法与内存槽相同），上传时按块等待它的读取；GPU 池里有的专家
  不读，从池里复制（池变了就补读）。`XTIER_COLD_READ_AHEAD=1`（默认）：本层的调用路由到 ≥ 90% 的冷专家时
  （`XTIER_COLD_READ_AHEAD_COVER`），同时把下一层的冷专家读进另一块暂存区（两块轮流），盘在这一层计算和下一层注意力期间不停；
  只路由到一部分的中等长度调用不预读（会白读）。1024–6144 token 的 split prefill 照常：CPU 拿一段内存槽里的专家
  （不读盘、不换槽），GPU 算其余的。
- **CPU prefill**（混合 prefill 的 CPU 部分）：一次调用要的专家（不在内存的 + 在内存里可换出的）超过可换出槽的一半时分批。

## 只存一份（模型比内存 + 显存还大时）

冷存储存全部专家，模型文件里的专家就成了第二份。`tools/cold_punch.py` 把这一份的空间还给硬盘：

1. 模型下到任何放得下的盘（峰值要模型 + 专家两份的空间），第一次按 `XTIER_COLD=1 XTIER_FAST_LOAD=1` 启动：写好 N 块盘上的记录，并记下每个
   专家张量在模型文件里的位置（第一个目录的 `KEY.ranges`，来自加载时的 `direct.locate`，不靠张量命名规则）。
2. 停服务，`tools/cold_punch.py MODEL --paths DIR:DIR... --dry-run`：逐字节比较记录和模型文件。
3. 去掉 `--dry-run`：比较全部通过才动手。先写标记文件 `XTIER-COLD-ONLY`，再用 `fallocate(PUNCH_HOLE)` 释放专家张量内的整块（向内对齐 4 KiB，
   张量外一个字节不动），恢复修改时间。文件大小、文件头、其他张量（注意力、草稿模型的专家等）都还在，SGLang 的加载器照常走一遍，XTier 不读被打洞的张量。

保护（`cold.require_checkpoint`、`cold_only`）：标记里的层只能从冷存储加载；没开冷专家、没开快速加载、不是部分缓存层、路径或存储名不对、记录缺失
都会让启动直接报错，绝不从全零的模型文件写记录。清单读不出来时也不再清空记录文件。标记还记着被打洞文件的大小和修改时间，模型文件换过（重新下载）
也会报错。模型目录的 .json 改了不影响（打洞后的层不再比较 `source`）。排名变了不用重写：记录的顺序以清单为准（`loadable`）。

`--restore` 把专家写回模型文件、再比较一遍、恢复修改时间、删标记；打洞中途崩溃也用它恢复。

代价：冷存储成了唯一一份（相当于 RAID 0），任何一块盘坏了都要重新下载模型；没有 XTier 的官方 SGLang 不能加载打洞后的目录（读到全零）。
TP 下每个 rank 只存自己那份，不记位置，也就不能打洞。

DeepSeek V4.1 Flash 1017 的副本实测（[报告](reports/2026-11-01-cold-pcie5.md)）：占用 290 → 21 GiB，核对加打洞 42 秒。

## 盘的要求

读法是 2.35 MB 的整片（片内顺序）、片的位置随机，不是 4K 随机读。实测（报告里四类盘的表）：没有 DRAM 的 PCIe 4.0 盘读大块
只比傲腾慢约 14%，PCIe 3.0 的盘慢 4 倍；要的是大块读带宽，不是 4K IOPS。无 DRAM 盘的数据放久后可能变慢，傲腾和有 DRAM 的
盘更稳。4 块三星 9100 PRO（PCIe 5.0，一张 x16 转接卡，四盘同读 50.6 GB/s，11-01）上每次缺失多花约 0.5 ms。
持续读也要测：HP FX700（无 DRAM）按这个读法满速读约 100 秒（约 460 GB）后塌到约 0.06 GB/s，温度正常、SMART 没有错误，
停下后约 7 分钟才恢复（10-27）；几秒钟的短测看不出来。一次缺失要等最慢的盘，一块会塌速的盘拖住整个池子。

池子大小由带宽决定：

- decode：每步缺失数 × 18.8 MB ÷ 带宽 = 每步多出的读盘时间（减去和计算重叠的部分）。缺失数随 X 超线性增长。
- prefill：每次 GPU prefill 调用要读 X × 289 GB × 路由到的冷专家比例；预读后，下限是每层冷专家字节 ÷ 带宽，低于每层计算
  加注意力的时间就完全藏住。

## 尾部跳过（`XTIER_TAIL_SKIP=R`，默认关，会改变输出）

参考 Strata 的 `STRATA_ROUTE_TAIL_SKIP`（它的默认是 top-10 里的第 7 名起，NVFP4 包默认关）。专家多、top-k 大、大部分专家在盘上时，
decode 每步读盘的大头是权重很小的路由。

- **规则**：一次最多 `XTIER_TAIL_SKIP_TOKENS`（默认 8）个 token 的 CPU 调用（decode 一步、单请求的投机验证窗口）里，不在内存的专家，
  如果每个 token 都把它排在第 R 名或以后（按该 token top-k 里的权重排，0 是最大，同权重按位置），就不读、不算：它的路由按 −1 处理
  （加 0），其余路由保持原来的权重，不重新归一化。在内存里的专家照算，prefill 不跳；不开冷专家、或 R ≥ top-k 时不起作用。
- **实现**：`csrc/engine/engine.cpp` 的 `tail_skip`，在换入之前改路由；跳过的专家数是引擎冷统计的第 7 项，日志
  `xtier cold: last 60 s` 那一行末尾的 `tail skip left out`。
- **测精度**：`XTIER_TAIL_SKIP_EVAL=1` 在 prompt 的 prefill 里按每个 token 套同一规则（被跳的路由权重置 0，`xtier/cache/tail.py`）。
  `bench/ppl_eval.py --top N` 导出每个位置最可能的 N 个 token，`bench/kl_compare.py` 拿它和不跳过的一次比：KL、首位 token
  改变比例、NLL 差。这样测比实际 decode 偏保守：实际验证窗口里要每个 token 都排得低才跳，而且 prompt 本身不跳。
- **实测**：见[报告](reports/2026-11-06-cold-units-tail-skip.md)。

## 否决

- **预门控预取**（用第 L 层的 MoE 输入和第 L+1..L+4 层的门控提前猜专家）：3001 个 token 的实测输入上，距离 1 的 top-6 只猜中
  59% 的冷专家路由，按 6 token 一步模拟预取，预读的只有 15–22% 被用上，读盘量变成 2.4–3 倍，只藏住约 37% 的缺失；
  多出的读盘先把盘占满（x30 每步要读 1.07 GB）。
- **常驻核心**（排名前 30% 永不换出）：x30、两块傲腾时 agent 长回复每步 69.4 ms，对没有常驻核心（GPU 池的专家初始计数 0）的
  57.4 ms；它把 GPU 池的专家钉在内存里，白占了 CPU 要用的槽。只去掉常驻核心、初始计数仍按排名时没有区别（GPU 池的专家几百步
  内仍占着内存）。代码已移除。
